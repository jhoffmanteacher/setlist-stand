# Setlist Stand — scope and decisions

Running list of what the app must do. Source for the work orders.

## Users
- One person per library. No shared libraries. Each user's songs, setlists and annotations sync across their own tablets through their own Google Drive.
- Others get music through **share packages** (see below), never a shared folder.

## Platform
- Web app installed from the browser (PWA), hosted on GitHub Pages. Android and iPad.
- Must work fully offline: app files, PDF libraries and every chart stored on the tablet. Sync only when online, and only when Jonathan taps Sync (2026-11-21): never on opening the app, never in the background, never while a song is open.
- Sync: Google Drive with the `drive.file` permission only. The app sees only the files it made itself, in its own "Setlist Stand" folder (no Google Picker, no script from Google).
- Repo: `jhoffmanteacher/setlist-stand` (public), code only — no PDFs in the repo.

## Must have
- Library of PDF charts; full-screen viewer; tap and swipe page turns; two pages side by side in landscape
- Each song is its own PDF file
- **Naming convention, title first**: `Song Title (version) - Artist.pdf` — e.g. "War Pigs - Black Sabbath.pdf", "Flowers in the Ashes (in G).pdf". Song, artist and version are separate fields; the library shows the song title first. Drive file names follow the same pattern.
- Annotation (pen, highlighter, eraser, undo), stored apart from the PDF
- **Text annotations** (MobileSheets library has 12 text boxes to carry over)
- **Annotations belong to the user, not the tablet**: the same person sees the same marks on their Android and their iPad
- Setlists with **drag-and-drop ordering** (drag handle only, no arrows)
- **Duplicate setlist** (Jonathan, 2026-11-22: on an open setlist it is in the **More** menu, with Gig date, Download PDF, Share, Rename and Collections; the bar keeps Play setlist, Add songs and Add break; the Setlists list is unchanged)
- **Breaks** inside a setlist; while playing, a break shows a full-screen break page with its name and the next song
- **Crop** margins, with a choice of one crop for the whole song or a crop per page
- **Split import** (done, WO2): one big PDF (songbook/fake book) becomes separate songs, using the PDF's bookmarks when present and hand-marked page ranges
- **New version** (was Replace chart; Jonathan, 2026-11-21): swap in a new PDF; the song keeps its place in every setlist and starts with fresh marks; the old chart, its marks and its crop are kept in Archived as "<song> (old YYYY-MM-DD)"
- **Collections** (Jonathan, 2026-11-21; this reversed "Collections (setlists cover it)" under Not doing): group songs and setlists by the band he plays them with, not the band that wrote the song. Each is named by him and can be renamed. A song or a setlist can be in more than one. One collection can be the default: the Library and Setlists open showing it, and new songs and setlists join it. One picker under the Library / Setlists tabs serves both. Share packages carry no collections (they are personal): songs and a setlist imported from a package join the receiver's own shown or default collection. Deleting a collection never deletes a song or setlist. The default is a setting of the tablet, not part of the library, a backup or a sync. MobileSheets' own collections are still not imported (the converter is unchanged).
- **Add songs in the order you tap them** (Jonathan, 2026-11-21: "pick songs for a setlist in the order of the setlist not just checkboxes"): in a setlist, tapping songs numbers them 1, 2, 3 (untapping renumbers), the button says "Add N", and they are added at the end in that order; the list stays A to Z. A search box in every song list.
- **Backup reminder after changes** (Jonathan, 2026-11-21; replaces "after 14 days"): the banner shows when something has changed since the last backup (any record except the PDFs), on the Library and Setlists tabs, never while playing. A restore counts as backed up until the next change.
- **Copy song** (Jonathan, 2026-11-21): Copy on a library row makes a second version of a chart (the same PDF marked up another way, say for another band). The person types the version name; the copy keeps the original's details, crop and marks (the marks are copied, not shared) and is in no setlist until it is added. Setlists keep using the original. Known limit: two songs with one PDF hash are two songs, so a share package holding both carries only one of them, and Add PDFs calls the second "already in your library".
- **Gig dates** (Jonathan, 2026-11-22): each setlist can have a gig date. The Setlists list shows upcoming gigs first (any year), then this year's past gigs, then setlists with no date, then earlier years folded away until tapped. Setlist names that already hold a full date ("Sf October 18 2026") are offered as gig dates once per tablet, never filled in without a tap; a name with no year, a day that does not exist, or two dates is left blank. Duplicate does not copy the date; share packages do not carry it (they are for another person; a package's setlist has no date).
- **Download setlists** (Jonathan, 2026-11-21; changed 2026-11-22): a setlist downloads as one PDF of its charts in setlist order (annotations optional), named with its gig date when it has one: this is the way to print a setlist. Download all does NOT make a PDF per setlist (each chart would be copied into every setlist that uses it, and the zip would grow with the number of setlists: 229 MB for his 12 setlists against 28 MB for the charts once). It gives one zip with every chart once (as stored, no marks) and a plain list file for each setlist, for the setlists the list shows; empty ones are skipped; above about 150 MB of distinct charts it is refused (a tablet holds the zip in memory about three times over).
- **Back swipe closes the song, not the app** (Jonathan, 2026-11-21): with a song open, the back gesture (Android's back, the iPad's edge swipe) closes one layer at a time: a message box first, then the Crop screen, then Annotate, then the song itself, back to the list it was opened from (the Library or the setlist). From a list (nothing open) back leaves the app as before: the app never traps him. Calls the writer made, not asked: back does exactly what Escape does at that moment, so a box that ignores Escape (a write in progress) ignores back too; a song from a setlist goes back to that setlist's screen.
- **Import a setlist from a text file** (Jonathan, 2026-11-21): Setlists -> **Import from a text file** (next to New setlist). One song per line; numbers and bullets at the start of a line are ignored; a line that says Break or `---` becomes a break; the setlist is named after the file. A line that matches no song is shown in a review box and left out (Add makes the setlist from the lines found and says how many were left out; Cancel changes nothing). A line that matches more than one song (two versions, or a copy) is chosen in the review box: each candidate shown as name (version) - artist, "(archived)" where it applies, or "Leave this line out". Calls the writer made, not asked: a line is matched against the full title, then the song name, then "Song - Artist" (case, accents, extra spaces, quote and dash styles ignored; archived songs match; every song in the Library, whichever collection is shown); a break is a line of three or more dashes, equals signs or asterisks, or "break", "set break" or "intermission" (optionally numbered, brackets and dashes around it ignored), and a Library song wins over a break; empty lines and lines starting with `#` are ignored; a file over 1 MB, with more than 500 song and break lines, that is not text, empty, or matches no song is refused in one sentence; UTF-8 (a byte-order mark taken off), UTF-16 with a byte-order mark, otherwise Windows-1252; a line over 200 characters is shown shortened as no match; a name in use gets "(2)" like a share package. Only the new setlist is written (one write, no gig date, the collections every new setlist gets); no song is ever made from a line. Not built: exporting a setlist to text, spreadsheets or pasted text, guessing at misspelled names.
- **Archive songs**: hidden from the library, still shown and playable in old setlists
- Print a setlist as one combined PDF (annotations optional); cropped songs print cropped
- Back up everything to one .zip; restore from it (Library → **Back up / Sync** → **Back up everything** / **Restore from backup**; Jonathan, 2026-11-22: these and the Google Drive control moved from the bottom of the Library into the Back up / Sync menu, next to Share / Import. **Sync with Google Drive** is in the same menu, and **Google Drive settings** opens a Google Drive box with Connect, Test connection, Disconnect and Sync; the bottom of the Library keeps one read-only line saying the Drive state. The reminder line keeps its own Back up now and Sync buttons.)
- **Share package**: export chosen songs or a whole setlist as one file with the PDFs and setlist order but **no annotations**; another user imports it into their own library. Songs already in their library are matched and not added twice.

## Technical notes
- Same user on two tablets: save each stroke with its own id and merge by id when syncing (deleted strokes kept as markers), so marks made on both tablets offline are never lost.
- Duplicate matching on import: fingerprint each PDF file's contents.
- MobileSheets setlist order = SetlistSong row order (no position column).
- Known limit: importing a share package holds every PDF of it in memory before the one write (like restore), so a very large package can fail on a tablet with little memory; nothing is changed when it does. The cap on one package's PDFs is 500 MB.
- Known limit: a share package holds every PDF in memory while it is built (about twice their total, like a backup), so a very large selection can fail on a tablet with little memory; nothing is changed when it does.
- Known limit: every song cut from a songbook carries its own copy of the fonts and images its pages use (pdf-lib copies what a page points at), so the songs together can take more space than the book did.
- Known limit: a restore holds the zip and every PDF in memory before it writes (about 3 times the zip's size), so a very large backup can fail on a tablet with little memory; nothing is changed when it does.
