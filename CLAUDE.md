# Setlist Stand

An installable web app (PWA) for a teacher and gigging musician who plays PDF charts from an Android or iPad tablet. Library of PDF charts, setlists, a full-screen viewer with page turns, pen/highlighter annotation, print and backup. It must work fully offline at a gig. One person per library, no sharing. Scope and settled decisions: `docs/DECISIONS.md`.

## Stack rules
- Vanilla JS as ES modules, plain CSS with CSS variables. No build step, no framework, no bundler: the repo files are the files GitHub Pages serves.
- No external URLs at runtime. Everything loads from this repo, with relative paths (the app lives under `/setlist-stand/`). The one exception (Jonathan, 2026-11-21) is Google Drive: the page may send DATA requests to `https://www.googleapis.com` (the CSP's `connect-src`) and navigates to `https://accounts.google.com/o/oauth2/v2/auth` to sign in. Those addresses, the Client ID and the scope live in `js/driveconfig.js` and nowhere else (`checks.mjs` enforces it). No script is ever loaded from Google (no Identity Services library, no Picker), and there is no client secret anywhere.
- Vendored libs in `vendor/`, exactly: pdf.js 3.11.174, pdf-lib 1.17.1, JSZip 3.10.1. Adding any other library, framework or build step needs Jonathan's OK.
- No music in the repo, ever. The repo is public.
- One job per file. Split a file when it starts doing two things or passes about 300 to 400 lines, and not before: do not cut a file only to make it shorter. Every new app file must be added to `PRECACHE` in `sw.js` (`checks.mjs` fails if it is not).
- Supported tablets: iPadOS 16 or newer, Android Chrome 100 or newer. Do not use a browser feature newer than that without a fallback (theme colours have fallbacks for `light-dark()`).

## Data model (as of v1 part 4)
- IndexedDB `setlist-stand`, version 2 (`DB_VERSION`), stores `songs`, `files`, `sets`, `ink`, `colls` (in-memory fallback if storage is blocked). The store names are ONE list, `STORE_NAMES` in `js/store.js`: the upgrade, the memory fallback and every loop over stores read it, and `snapshot()` in `tools/loops/harness.mjs` reads the names from the database, so a store added later is carried everywhere. The upgrade from version 1 only creates `colls` (`createObjectStore` for the stores that are missing), so every record, PDF and ink page is kept. A tab still running the old version-1 app blocks the upgrade until it is closed (it cannot be told to let go): `ss-db-blocked` is fired and `js/main.js` says "Close the other Setlist Stand tab"; a tab on this version closes its connection on `versionchange` (`ss-db-changed`: it asks for a reload).
- Song `{id, title, song, artist, version, archived, colls, pages, hash, added, updated}`. `title` is derived: "Song (version) - Artist" (empty parts left out). `hash` is SHA-256 of the PDF bytes. Old records (title only) are upgraded on load with the splitter in `js/names.js` (a port of `split_name()` in `tools/msb_convert.py`; `node tools/names-parity.mjs <.msb>` must print "N of N match"). New imports use `js/importname.js` (title-first file names, legacy names fall back to the splitter). PDF bytes live in `files`, keyed by song id.
- Song order (library, Archived list, search results, the pickers for "Add songs" and "Share songs"): A to Z by song name, `compareSongs` in `js/names.js` (`Intl.Collator`, sensitivity 'base', numeric; ties by artist, version, then id). Every word counts: a leading "The", "A" or "An" is NOT skipped (Jonathan, 2026-11-21). It is made when a list is drawn (`renderLib()`, `pick()`); nothing is stored in that order and no song is written. The order inside a setlist is the user's own. "Add songs" on a setlist picks in TAP order (`pick(…, {ordered:true})` in `js/util.js`): each song tapped gets the next number (shown where the tick box is), tapping a numbered song removes its number and the later ones move up, the button reads "Add N", and the songs are added at the end of the setlist in number order (one number per song per dialog). Every `pick()` has a search box (`songMatches` in `js/names.js`, the same match as the Library's); numbers and ticks survive a search that hides them and the count still counts them; the search box does not take focus on open (the tablet keyboard); Share songs and "Add songs to a collection" are unordered and return list order.
- Song crop (optional): `crop: {all: rect|null, pages: {"<page number>": rect}}`, rect `{x, y, w, h}` as fractions of the FULL page (x, y = top-left of the kept part). A page's own crop wins over `all`. `cropOf(song, pn)` in `js/store.js` is the one place that decides. The viewer draws only the kept part, scaled up; print sets the page's CropBox (after drawing marks against the uncropped page).
- Split a songbook (`js/split.js`, `js/songlist.js`, `js/songpdf.js`): one big PDF becomes separate songs, each saved exactly like an added PDF (the PDF and its record in ONE `putAll`); the book itself is never saved. Pages are copied with pdf-lib after taking off everything that points at other pages, and every song is checked page by page (it holds only its own pages, never part of a chart cut away); a protected, password-locked, layered or ambiguous book is refused, never cut; a run has a space budget; no dates are written, so the same pages always give the same hash and a book split twice is all duplicates. Full rules: `.claude/rules/split-share.md`.
- Share package (`js/sharepack.js`, `js/share.js`, `js/shareimport.js`): chosen songs, or a setlist, as one zip (`share.json` + `files/<id>.pdf`, its own `SHARE_VERSION`) that carries details and crops and NEVER marks, archive flags, timestamps or titles; the PDFs are the stored bytes (never re-saved), so the SHA-256 is the same on both tablets. Import treats the file as untrusted and checks EVERYTHING before anything is written (file and zip limits, the CRC of `share.json`, every PDF's SHA-256, ids, counts, crops); songs already here (same hash) are left exactly as they are, nothing is overwritten, one confirm, and ONE `putAll` writes the lot. Full rules: `.claude/rules/split-share.md`.
- New version (`newVersion()` in `js/library.js`, the button that replaced Replace PDF; Jonathan, 2026-11-21): the song keeps its id, details, crop and setlist places (no setlist is written) and takes the new PDF, `pages` and `hash`; its marks are cleared as before (deletion markers through `reconcile`; ink of pages past the new end removed). The old chart becomes a NEW song (`newSong`, id from `unique()` in `js/shareimport.js`), `archived:true`, in no setlist: the stored PDF bytes copied as they are (hash unchanged), `version` + `old YYYY-MM-DD` (local date, the whole kept within 200 characters: "War Pigs (old 2026-11-21) - Black Sabbath", "(in G, old 2026-11-21)"), the crop, and every page's live strokes and notes under the new id (ids, points, `updated` unchanged; deletion markers not copied). Order: the duplicate question (if the new PDF is already in the library), then one confirm (`modal()`), then ONE `putAll` (files, ink, songs). If the stored PDF cannot be read, the confirm says so, the new chart still goes in and no copy is made. If the song was edited or deleted while the dialogs were open, nothing is written.
- Copy song (`copySong()` in `js/copysong.js`, the Copy button on a library row; Jonathan, 2026-11-21): a second version of a chart (the same chart marked up another way for another band). The copy is a NEW song: fresh id (`unique()`), the original's record carried over by spreading a deep copy (so a field this code does not know is kept), `version` = what the person typed (required; the original's own version, case and spaces ignored, is refused in the dialog), `archived:false`, fresh `added`/`updated`, the same `pages`, `hash` and `crop`; its PDF is the stored bytes copied as they are (hash equal to the original's); every page's LIVE strokes and notes are copied with fresh ids and `updated` (deletion markers not copied). Song, PDF and marks are ONE `putAll`. The copy is in no setlist; the original, its marks and every setlist are untouched. Two songs may therefore share one PDF hash: songs are matched by id, never by hash (Add PDFs, share import and split still match by hash and are the known limit).
- Text notes live in the same ink list as strokes: `{id, t:'text', x, y, text, size, c, updated}`, x,y = top-left as full-page fractions, size = font size as a fraction of page width (small .012, medium .018, large .028). The eraser does not touch them. They undo, print and back up like strokes.
- Set `{id, name, items:[{type:'song', id} | {type:'break', id, name}], colls, gig?, created, updated}`. `gig` is an optional gig date, a plain calendar date `'YYYY-MM-DD'` (no time, no time zone), absent when there is none (Jonathan, 2026-11-22). `js/gigdate.js` (pure: `validGig`, `gigOf`, `cleanGig`, `dateInName`, `groupSets`) reads it, `js/gigui.js` asks for it. A `gig` that is not a real date is IGNORED when a list is drawn (`gigOf`: the setlist sits under "No date", like `cropOf()` ignores a damaged rectangle), dropped and counted by a restore (`restoreFrom()`: "N gig dates that were not real dates were left out"), and NEVER makes `setProblem` refuse a set (sync skips a set that fails it). Changing or clearing it goes through `saveSet` (stamps `updated` with `stamp()`); Duplicate does not copy it; share packages do not carry it (`SHARE_VERSION` and `BACKUP_VERSION` unchanged). The Setlists list is grouped when any setlist has a date: Upcoming (today or later, any year, soonest first), this year's past gigs (newest first), No date, then each earlier year (newest year first, collapsed to start; open or closed is kept in memory only). With no dated setlist the list is flat and has no headers. The one-time fill-in (`offerFill()` in `js/gigui.js`, localStorage `ss-gig-fill`, per tablet, set when the person answers or a write went through): setlists without a gig whose name clearly holds a full date (month name with day and 4-digit year either order, `YYYY-MM-DD`, `M/D/YYYY`; the date must exist; exactly one per name; no lookbehind in the regex, iPadOS 16.0 to 16.3 cannot parse one) are listed with tick boxes; Fill in writes the ticked ones in ONE `putAll` after re-reading each (`gig` and `updated` only, names never change). On a tablet where `driveSetUp()` is true (signed in, or synced before) it is offered ONLY within 10 minutes of a finished sync (`lastSync()`): otherwise this tablet's copy of a setlist may be older than the other tablet's, and the fill-in would stamp the old copy newer so a later sync lets it win (the other tablet's added songs lost); a sync that brings the other tablet's dates in makes those setlists drop out of the offer. A tablet that never uses Drive is offered it as before. Old sets with a `songs` array are upgraded on load and on restore (`upgradeSet`). A song can appear twice; rows are identified by position. Breaks are not songs: print skips them, the viewer shows a full-screen break page (name and "Next: <song>"), and the song before a break says "Next: <break name>". Reordering is drag and drop from the handle (pointer events, `initSetlists()` in `js/setlists.js`); there are no up/down buttons; with a handle focused, ArrowUp/ArrowDown move the row (keyboard reorder).
- Download setlists (Jonathan, 2026-11-21; Download all changed 2026-11-22): the open setlist's item is Download PDF in its More menu (it was the Print PDF button; `printDialog()` and `buildSetPdf()` in `js/print.js` are unchanged apart from the title "Download <name>"): one PDF of its charts in order, with marks if ticked, saved to the downloads, named by `setFileName()` (the gig date first when there is one: "2026-10-18 Sf October 18 2026.pdf"). This is the printing route. Download all (`js/downloadall.js`, the button in the Setlists list bar) is NOT a PDF per setlist (that copied every chart into every setlist and grew with the number of setlists): it makes one zip, `Setlists - Setlist Stand.zip` (`Setlists - <collection> - Setlist Stand.zip` with a collection shown), stored without compression, with `Songs/<title>.pdf` (every distinct chart of the setlists the list shows ONCE, the stored bytes exactly as they are, no marks) and `Setlists/<name>.txt` (one list file per setlist: name, gig date in words, songs numbered and breaks as `--- name ---`; named with the gig date; " (2)" on a clash, case ignored, for songs and for setlists). Setlists with no songs are skipped. A song with no stored PDF is listed with "(no PDF on this tablet)" and named in the final box. Before any work the size of the distinct charts is checked against `limits.maxBytes` (150 MB, an exported object so a test can lower it; the zip is held in memory about three times over) and refused with "Too much to make at once". Stop at any point downloads nothing. Nothing is written to the library and no PDF is changed. `fileName()` in `js/util.js` turns slashes into "-", drops control characters, composes letters (NFC) and cuts to 150 characters.
- Ink: key `songId:pageNumber` -> `{updated, strokes:[...]}`. A stroke is `{id, t:'pen'|'hl', c:'#rrggbb', w:<fraction of page width>, p:[[x,y],...], updated}`; a pen's `w` is one of three values, thin `.002`, medium `.003` (what the pen always drew) or thick `.005` (`PEN_W` in `js/ink.js`; strokes saved earlier may hold any width and keep it), the highlighter's is `.02`; x and y are fractions (0 to 1) of the full page. Keep them that way. An erased stroke becomes `{id, deleted:true, updated}`. Older data stored a bare array without ids; `upgradeInk()` fixes it on first read.
- Collections (`js/collections.js`; Jonathan, 2026-11-21): the band or group a song or setlist is played with, named by him. Store `colls`, record `{id, name, created, updated}`; deleted ones are `{id, deleted:true, updated}` like songs. A song or setlist lists its collections in `colls` (a list of ids, `[]` by default, filled in by `upgradeSong` / `upgradeSet` through `cleanColls`; one song or setlist may be in several; an id of a deleted or unknown collection stays in the record and is ignored when a list is drawn). The upgrade writes `colls: []` on every existing record in ONE `putAll` in `load()` and does not touch `updated`. Names: required, trimmed, at most 200 characters, unique case-insensitively (`askName`). Deleting a collection removes its id from every song and setlist in the SAME `putAll` as its marker and stamps `updated` on each of those records and the marker (a later sync carries a change only when `updated` moves); it never deletes a song, PDF, marks or setlist. Records are changed by spreading the existing one (a field this code does not know is kept; `roundtrip` has a test). Picker under the tabs on the Library and the Setlists list: "All", each collection A to Z (the default marked), and a Collections button (alone until a collection exists); the collection shown is in memory only, so the app opens on the default (or All); an open setlist always plays all its songs; "Add songs" in a setlist lists the shown collection's songs with a "Show all songs" switch (`pick(…, {all})`). Manager dialog (`openManager()`): Rename, Set as default (tap Default again to clear), Add songs, Delete (two taps), New collection. Edit song and an open setlist's Collections button have tick boxes (`form(…, checks)`). New songs (Add PDFs, every split song, share import) and new setlists (New setlist, share import) join the collection shown, or the default when All is shown (`joinColls()`); Duplicate setlist and Copy song carry the original's; New version's archived old chart keeps the song's; a song matched by share import is left as it is. Share packages carry no collections (`SHARE_VERSION` unchanged). Songs are matched by id, never by hash, for collections and Copy.
- Deleting a song or setlist leaves `{id, deleted:true, updated}` in its store (the song's PDF and ink pages are removed). The UI never shows markers; backups include them. This is so Google Drive sync can tell "deleted" from "never had it": merge by id, newest `updated` wins. Every place that changes an EXISTING record stamps it with `stamp(prev)` in `js/store.js` (`max(now, prev.updated + 1)`), so a local edit always beats the version it was made from, even a copy from a tablet whose clock is ahead; new records use `Date.now()`. `putAll` ops may carry `ifUpdated` (the `updated` the record must still have, `null` = absent): a mismatch aborts the whole transaction and rejects with an error named `StaleWrite`. The records a deletion writes are built in `js/deleteops.js`.
- Archived songs are hidden from the library (shown with "Show archived"), but still show and play in setlists.
- Small settings live in the browser's own storage, never in IndexedDB: `localStorage` `ss-two` (two pages), `ss-pen-w` (pen thickness: `thin`, `medium` or `thick`; default medium), `ss-gig-fill` (the gig-date fill-in was answered, per tablet), `ss-default-coll` (the id of the default collection, per tablet: never in the library, a backup or a sync; one that points at a deleted collection counts as none), `ss-last-backup` (time of the last backup download, for the nudge), `ss-problems` (the private problem log: last 30 errors, never sent anywhere), `ss-last-sync` (when this tablet last finished a sync, for the sync reminder; never synced), `ss-sync-intro` (the first-sync note was read); `sessionStorage` `ss-resume` (the open song, put back after an update reload).
- Restore (`restoreFrom`) checks everything first (zip CRC, `library.json` ours and not from a newer version, every song's PDF present and matching its hash) and then writes all five stores in ONE transaction (`putAll`; collections too, a deletion marker only winning over a newer collection here): it is all or nothing. A box (`busy()` in `js/util.js`) says "Opening the backup…", "Checking song N of M…", "Saving to this tablet…"; Stop (or Escape) works while it is only reading and checking and changes nothing ("Restore stopped. Nothing was changed."), and from the write on Stop is gone (`job.lock()`). Back up has the same box ("Packing song N of M…", "Making the backup file… N%"): Stop at any point downloads nothing and does not set `ss-last-backup`.
- Backup is a zip: `library.json` `{app:'setlist-stand', version:3, songs, sets, colls, ink, ...}` plus `files/<id>.pdf`. Versions 1 (the prototype and the converter's output) and 2 (before collections) must keep restoring, with no collections. `BACKUP_VERSION` is only the gate in `restoreFrom()`; the per-record checks in `js/backup.js` (`ID_RE`, `LIMITS`, `okId`, `okText`, `okPage`, all exported) do not depend on the version. A song's or setlist's `colls` must be a list of plain ids (a bad id refuses the backup; an unknown id is healed by being ignored), a collection needs a plain id and a short name.
- Google Drive connection (js/driveconfig.js, js/googleauth.js, js/drive.js, js/syncui.js): sign-in is Google's implicit redirect flow, `drive.file` scope only, no server, no secret. The token is kept IN MEMORY ONLY (never in any storage, a backup or a share package: closing the app, a reload or an app update signs out), and only the `Authorization` header carries it. The page's `#` answer is read and removed first thing (`takeReturn()` in `js/main.js`), checked against a one-time note (`ss-google-pending`). The home folder "Setlist Stand" is found by type and a private mark, not by name. Nothing talks to Google except when the person taps Connect, Sync, Test connection or Connect again, never while a song is open. Full description and the list of failures and messages: `.claude/rules/drive-sync.md`.
- Google Drive sync (js/sync.js, js/syncmerge.js, js/driveops.js, js/syncdialogs.js, js/deleteops.js): started only by a tap on Sync. It syncs songs, setlists and collections as WHOLE records (every field kept) plus each song's PDF; not ink yet (Part 3), not per-tablet settings. Merge is by id and `updated` only, never by title or PDF hash (Copy song makes two songs with one PDF): the larger `updated` wins, a deletion marker is just a record, absence is never deletion, and a deletion made on the other tablet is only LISTED (Delete here, two taps / Keep), never applied on its own. Downloads come first, then the person's answers, then uploads; a song's PDF and record are written in ONE `putAll` with `ifUpdated`; a chart a sync would replace is kept as an archived copy; everything from Drive is checked like a restore and a bad record is skipped and named. `ss-last-sync` and `ss-sync-intro` are per tablet. Layout in Drive, the order of a run, limits and every rule: `.claude/rules/drive-sync.md`.

## Don't overload Jonathan's Mac
The browser tests start Chromium (and a long run starts hundreds of pages), and helper agents each start their own. Several at once make the Mac crawl. Rules, for Claude and for every helper agent it starts:
- **At most two browser runs at a time** (Jonathan, 2026-11-21; it was one). `tools/smoke.mjs` and `tools/loops.mjs` take one of two lock directories in the temp folder (`setlist-stand-browser.lock`, `setlist-stand-browser-2.lock`; `tools/loops/slot.mjs`) and wait for a free one. After taking it, a run waits (up to 5 minutes) until the 1-minute load is below 75% of the cores AND the CPUs were really less than 70% busy over the last two seconds. Never bypass it: a scratch script that calls `chromium.launch()` must call `await acquireSlot('<name>')` first. `SS_NO_SLOT=1` is for CI runners only; `SS_SLOTS=1` gives the old one-at-a-time rule. Measured on this Mac (Intel i5, 8 logical cores, 16 GB; 2026-11-21): idle it sits at a load of 1 to 2.5, each active run adds about 2 (a Chromium run is about 1 core and 600 to 800 MB, plus the node test process), and THREE at once, measured twice, gave a load of 7.4 on average with a peak of 10, and then 5.85 with a peak of 8.4 (the start gate bypassed, a second Claude program busy at the same time): three sits at the limit on average and over it for the first 20 seconds, so TWO is the default; three is possible for one run when nothing else is busy (`SS_SLOTS=3`). A run that is stuck for many minutes at 0% CPU (an orphan whose parent is gone) holds its slot: look at `ps` and tell Jonathan, do not queue behind it.
- **Helper agents:** several may write code at once if each has its own files (that costs the Mac little), but never more than four, and their browser runs all go through the two slots above, so at most two of them test at a time. A helper that is waiting on a slot is fine; starting a browser without a slot is not. Prefer two or three agents; use four only for clearly separate files.
- **Heavy runs go to GitHub, not this Mac** (Jonathan, 2026-11-22). The full `smoke` and the full `loops` run on GitHub's own computers for free (`.github/workflows/browser.yml`, Chromium, about 40 minutes) after every push to `main` and after a push to a branch named `ci-try/<anything>`. So to test a commit before it goes to `main`, push that commit to `ci-try/<work-order>-<n>` (`git push origin <commit>:refs/heads/ci-try/<name>`), then read the result from GitHub (`curl -s "https://api.github.com/repos/jhoffmanteacher/setlist-stand/actions/runs?branch=ci-try/<name>"`; the job annotations name the failing loop and the artifacts hold the whole output) instead of running the whole suite here. Run LOCALLY only: `--only` for what you changed, WebKit (`SS_BROWSER=webkit`), and `plant-faults` (the workflow does none of those). Branches pushed only for tests or reviews (`ci-try/*`, review snapshots) are deleted when the work order is done.
- **Run only what the change needs.** Use `--only <text>` for one loop, not the whole suite after every edit. Run the full `smoke` and `loops` once, at the end of a part. Three clean runs in a row only for a loop that has just flaked, not as a habit.
- For a run longer than a few minutes (the full suite, `plant-faults`), start it as `caffeinate -i node ...` so the Mac does not sleep part-way: a sleep makes timers fire at wake and shows up as bogus failures (a fault "got through" after 30 minutes, a check that "does not parse"). Re-run the single case on its own before believing such a result.
- No watch modes, no polling loops that start a browser, no second dev server while one is running. Check `uptime` before a long run; if the load average is above the core count, wait.
- GitHub runs the full walk after every push (`.github/workflows/browser.yml`); a run on the Mac is for the area just changed.

## Best practices already in place (keep them)
- **Security:** a Content-Security-Policy meta in `index.html` (`'self'` only, no `eval`, no outside hosts except `https://www.googleapis.com` in `connect-src` for the Drive connection, `isEvalSupported:false` for pdf.js); no inline script; no outside request at runtime except those Drive data requests. `tools/checks.mjs` pins the whole policy: loosening it needs Jonathan's OK and a change to the pinned policy in the same commit. `docs/THIRD-PARTY.md` lists every vendored file and its license: add a row and the license text in the same commit as any new vendored file.
- **Data safety:** a backup reminder (`js/nudge.js`, drawn into `#libNudge` on the Library, the Setlists list and an open setlist, never in the viewer): it shows when something has CHANGED since the last backup, not by days (Jonathan, 2026-11-21): any record in any store but `files` (songs, setlists, collections, ink pages, deletion markers) whose `updated` is later than `ss-last-backup`, or, with songs and no backup ever, "You have not backed up yet."; the wording is "Changes since your last backup (today / yesterday / N days ago)." with Back up now. `js/store.js` keeps the newest `updated` in memory (`newestChange()`): `put()`, `putAll()` and `update()` are the only write paths and each tells `seen()` what it wrote once the write has gone through (a plain delete counts as now; a write whose `updated` is not newer, like a restore of old records, a hash filled in or the upgrade's `colls: []`, changes nothing); `load()` reads it from the songs, setlists and collections, `initChanged()` from the ink pages once after the first draw; `ss-changed` is fired when it moves and the reminder redraws without a reload. A restore sets `ss-last-backup` (so a restored library is backed up until the next change); a stopped backup changes nothing. Measured on the 74-song converted library: first Library draw 176 ms before, 185 ms after (noise), the ink scan 15 ms after the draw. Drive sync adds its Sync button to this same line, a storage line (used, free, protected or not, "Ask the browser to protect it"), a restore that is all or nothing, a refusal of backups from a newer version, and plain-language errors ("The tablet is full...") through `explainError`. Duplicate PDFs (same hash) are skipped unless Jonathan says "Add anyway".
- **Accessibility and tablet:** every dialog goes through `modal()` (role=dialog, focus trapped and restored, Esc cancels, the page behind is inert); setlist rows reorder by keyboard (handle focused, ArrowUp/ArrowDown); safe-area insets, no rubber-banding or text selection in the viewer, no double-tap zoom delay.
- **Updates:** a new version waits for a tap on "Updated. Tap to reload" (never mid-song); only that tab reloads; the open song comes back.

## Closed-loop tests (`node tools/loops.mjs`)
`tools/smoke.mjs` does an action and checks the result. A **closed loop** takes what an action *produces* (a backup zip, a printed PDF, a deployed file, a reloaded page) and feeds it back through an independent path (restore it, render it with pdf.js, hash it, read the source of truth), then compares with what went in. Nothing is mocked, with ONE exception: real Google cannot be reached from a loop, so `tools/loops/fake-google.mjs` stands in for Google's two addresses at the network edge (Playwright `context.route`); the app's own code, storage, service worker and CSP run for real, and the stand-in behaves like Drive (paging, `fields`, `appProperties`, 401, 403 full, 429, 5xx, CORS). Real Drive is tested by Jonathan on his tablets. Loops live in `tools/loops/*.loop.mjs` (each exports `loops = [{name, needs?, run(ctx)}]`; helpers in `tools/loops/harness.mjs`). `node tools/loops.mjs --list` shows them; `--only <text>` runs some; `--root <dir>` tests a scratch copy; `--live <url>` adds the deployed-site loops; `--seed N --case N --verbose` replays one case of the random loop. A loop whose private input is missing (`needs`) prints SKIP, never FAIL: the MobileSheets files are found in the main checkout's untracked `Claude outputs/` (or `SS_MSB` / `SS_LIBRARY_ZIP`) and are never copied or committed.

## Checks
- `node tools/checks.mjs`: syntax of `js/*.js` and `sw.js`; every precached file exists and every app file is precached; no `http(s)://` in app code (except the four Google addresses in `js/driveconfig.js`, spelled out one by one); the Content-Security-Policy equals the pinned policy; no Google client secret anywhere; no `window.claude`; `VERSION` in `sw.js` changed if a precached file changed.
- `node tools/checks.mjs --bump`: writes a new `sw.js` VERSION.
- `node tools/smoke.mjs`: Playwright run at 1280x800 (add, open, page turns, draw, reload, offline reload, setlist, print, backup/restore).
- Safari engine: `SS_BROWSER=webkit node tools/smoke.mjs` (and `SS_BROWSER=webkit node tools/loops.mjs --only roundtrip` etc.) runs the same walk in Playwright's WebKit (`node node_modules/playwright/cli.js install webkit` once). Chromium-only loops (CDP: update, kill switch, offline h) skip themselves. See `tools/README.md`. Run it after dialog, focus, storage or pointer changes; touch drag on a real iPad is still untested.
- `node tools/lint.mjs`: ESLint (fetched by npx at the versions pinned in `eslint.config.mjs`, nothing installed) for undefined names, dead code and similar slips in `js/`, `sw.js` and `tools/`. Report-only (`--verbose` lists warnings, `--strict` exits 1 on errors); GitHub runs it as the `lint` job.
- Git hooks in `.githooks/` (enable once per clone: `git config core.hooksPath .githooks`). `pre-commit` refuses `.msb`, `.zip`/`.pdf` outside `tests/fixtures/`, anything in `Claude outputs/`, and staged JS that does not parse. `pre-push` runs `node tools/checks.mjs` on a push to `main` (HEAD, clean tree) and refuses on a FAIL; branch pushes pass. Bypass: `--no-verify`.
- Stop hook (`.claude/hooks/stop-checks.mjs`, `.claude/settings.json`): at the end of a turn that changed code files it runs `node tools/checks.mjs` and sends failures back (the "VERSION bumped" line is expected and ignored; at most 3 times a turn). Off switch: `SS_STOP_CHECKS=0`.

## If it goes wrong
`BREAK-GLASS.md` (repo root) is the plain-language page for Jonathan: a bad update on a tablet, a broken site, a lost library. `tools/kill-switch/kill-sw.js` is the emergency service worker that clears the app's caches and never touches the library; `node tools/loops.mjs --only kill` proves it. Keep that page true whenever the service worker or update flow changes.

## Working with agents
- **Use agents and sub-agents when they fit: this is a rule, not an option.** Hand work to an agent when it is independent of what the main session is doing, is read-only or touches its own files, or needs a view that is not anchored on the main session's: adversarial review (always, for risky areas), a measurement script written while the main session builds, mechanical runs, scouting a subsystem. Do the work yourself when it is a handful of tool calls or a lookup whose answer you need before the next step. Every limit below still applies (at most four at once, one browser run at a time, and a helper that is waiting on the browser slot is fine).
- **The main session decides the model and the effort of every agent it starts, for that job.** Neither is inherited by default and neither is fixed by a table: set `model` and `effort` (`low` to `max`) on each call as the work deserves, weighing how much a missed mistake would cost against the time and tokens spent. Sonnet and Opus are both fine; so is any effort. **Floor for risky cases:** an adversarial review of the data layer, restore, the service worker or print (and anything on the "Never" list) runs on Opus at `high` effort or more: the main session may go higher, never lower, because it is the one whose work is being checked and is least able to judge how hard to look. A work order's own "session effort" line is about the main session and does not cap its agents. Report the choice in one line when it is not obvious.
- **Local agents** work in the worktree and may edit code. Give each its own files, tell it not to touch `CLAUDE.md`, `.claude/`, `.githooks/`, workflows or the `sw.js` VERSION, and keep to at most four at once (see "Don't overload Jonathan's Mac").
- **Cloud agents** (`isolation: remote`) are read-only reviewers. They see only what has been pushed to a branch, so push the branch first and pin the review to that commit.
- **Saved roles:** `.claude/agents/setlist-reviewer.md` (adversarial review) and `setlist-runner.md` (mechanical runs) hold a starting model and effort. They are defaults, not rules: the main session may override either one on a call.
- **Review:** an adversarial reviewer reports findings as file:line, the quoted code, the failing input and the smallest fix. After fixes, a FRESH reviewer re-reviews, not the one that found them.
- **Reports:** at most 20 lines. Treat what an agent says as a claim: read the diff and run the check yourself before relying on it.
- **Rules for each area** are in `.claude/rules/` (service worker, data and backup, viewer and print, dialogs and CSP, Google Drive sync, splitting and sharing).

## Worktree and push rules (from the work order)
- Work in your own worktree, never the main folder: `git fetch`, then `git worktree add ../setlist-stand-wo-<name> -b wo/<name> origin/main`. Run `git worktree list` first; if another worktree has unpushed work in the same files, stop and ask.
- Start every part with `git fetch` and `git rebase origin/main`. Ship each part (push) before starting the next.
- Write `CHANGELOG.md` and bump the `sw.js` VERSION last, after the final rebase, in the part's last commit.
- Push: fetch, rebase if `origin/main` moved, run `node tools/checks.mjs` on the rebased tip, then `git push origin HEAD:main`. Fast-forward only. No merge commits, no force-push.
- If a rebase conflicts in anything besides `CHANGELOG.md` or the `sw.js` version line, stop and ask.
- Files for Jonathan (screenshots, converted backup) go in the main folder's `Claude outputs/`. It is untracked and gitignored; a copy left in a worktree is deleted with it.
- After the last push: fast-forward the main folder if clean, confirm `git cherry origin/main wo/<name>` shows no `+`, then remove the worktree and branch.
