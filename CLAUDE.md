# Setlist Stand

An installable web app (PWA) for a teacher and gigging musician who plays PDF charts from an Android or iPad tablet. Library of PDF charts, setlists, a full-screen viewer with page turns, pen/highlighter annotation, print and backup. It must work fully offline at a gig. One person per library, no sharing. Scope and settled decisions: `docs/DECISIONS.md`.

## Stack rules
- Vanilla JS as ES modules, plain CSS with CSS variables. No build step, no framework, no bundler: the repo files are the files GitHub Pages serves.
- No external URLs at runtime. Everything loads from this repo, with relative paths (the app lives under `/setlist-stand/`). The one exception (Jonathan, 2026-11-21) is Google Drive: the page may send DATA requests to `https://www.googleapis.com` (the CSP's `connect-src`) and navigates to `https://accounts.google.com/o/oauth2/v2/auth` to sign in. Those addresses, the Client ID and the scope live in `js/driveconfig.js` and nowhere else (`checks.mjs` enforces it). No script is ever loaded from Google (no Identity Services library, no Picker), and there is no client secret anywhere.
- Vendored libs in `vendor/`, exactly: pdf.js 3.11.174, pdf-lib 1.17.1, JSZip 3.10.1. Adding any other library, framework or build step needs Jonathan's OK.
- No music in the repo, ever. The repo is public.
- One job per file. Split a file when it starts doing two things or passes about 300 to 400 lines, and not before: do not cut a file only to make it shorter. Every new app file must be added to `PRECACHE` in `sw.js` (`checks.mjs` fails if it is not).
- Supported tablets: iPadOS 16 or newer, Android Chrome 100 or newer. Do not use a browser feature newer than that without a fallback (theme colours have fallbacks for `light-dark()`).

## Data model (as of v1 part 4)
- IndexedDB `setlist-stand`, version 1, stores `songs`, `files`, `sets`, `ink` (in-memory fallback if storage is blocked).
- Song `{id, title, song, artist, version, archived, pages, hash, added, updated}`. `title` is derived: "Song (version) - Artist" (empty parts left out). `hash` is SHA-256 of the PDF bytes. Old records (title only) are upgraded on load with the splitter in `js/names.js` (a port of `split_name()` in `tools/msb_convert.py`; `node tools/names-parity.mjs <.msb>` must print "N of N match"). New imports use `js/importname.js` (title-first file names, legacy names fall back to the splitter). PDF bytes live in `files`, keyed by song id.
- Song order (library, Archived list, search results, the pickers for "Add songs" and "Share songs"): A to Z by song name, `compareSongs` in `js/names.js` (`Intl.Collator`, sensitivity 'base', numeric; ties by artist, version, then id). Every word counts: a leading "The", "A" or "An" is NOT skipped (Jonathan, 2026-11-21). It is made when a list is drawn (`renderLib()`, `pick()`); nothing is stored in that order and no song is written. The order inside a setlist is the user's own.
- Song crop (optional): `crop: {all: rect|null, pages: {"<page number>": rect}}`, rect `{x, y, w, h}` as fractions of the FULL page (x, y = top-left of the kept part). A page's own crop wins over `all`. `cropOf(song, pn)` in `js/store.js` is the one place that decides. The viewer draws only the kept part, scaled up; print sets the page's CropBox (after drawing marks against the uncropped page).
- Split a songbook (`js/split.js`): one big PDF becomes separate songs, each saved exactly like an added PDF (`newSong` in `js/store.js`, PDF and record in ONE `putAll`). The book itself is never saved. A draft row is `{id, on, title, from, to}` (`to` null = the page before the next row, rows sorted by `from`, a row that is not ticked still ends the row before it, two rows may share a page). Draft rows come from the PDF's bookmarks (leaf bookmarks only; "Cover", "Contents", "Index" start unticked) or from tapping a page. `makeSongPdf` copies the pages with pdf-lib after taking off everything that points at other pages (Link annotations, and on the other annotations /P, /A, /AA, /Dest, /IRT and a widget's /Parent; on the page /B and /AA): pdf-lib copies whatever a page points at, so one such pointer on every page would put the whole book in every song. Nothing is ever taken out of a page's content or resources (a song must never lose part of a chart). It then counts the page objects it wrote; if the song holds any page besides its own it drops the notes from the song (never from the book) and tries once more, then refuses (`error.cut`) and the song is never saved; a run has a space budget (`budgetFor`: the larger of 150 MB and three times the book; the weight of a song, the size of its streams, is checked before it is saved): a book that makes every song as heavy as the whole book (one list of every picture for all pages) stops the run with a plain message after a few songs instead of filling the tablet, the songs not added stay ticked; one song that cannot be cut does not stop the others. Page dictionaries are never edited by deleting and re-adding a key (that reorders the key and changes the bytes, so the same pages would stop giving the same hash). It writes no dates, so the same pages always give the same bytes and hash: a book split twice is spotted as duplicates and skipped (unless "add again" is ticked); only the library as it was before the run counts, because two songs on one page are the same bytes and both belong. A protected PDF (`isEncrypted`), a password-locked one, one with layers switched off by default (asked of pdf.js) or content tagged with a layer rule (`/OCMD`, as an object or inline; the songs would show what the book hides), and one whose page tree pdf.js and pdf-lib read differently (a song would be cut from other pages than the ones shown) are refused, never cut. Typed titles go through `parseTypedTitle` (taken as typed), not the old-file-name guessing of `parseFileName`. A run that fails or is stopped leaves the screen open with the songs not yet added still ticked. Text notes, crops and marks do not apply: the songs start fresh.
- Share package (`js/sharepack.js`, `js/share.js`): chosen songs, or a setlist, as one zip with `share.json` and `files/<id>.pdf`. `share.json` is `{app:'setlist-stand', kind:'share', version:SHARE_VERSION, saved, songs:[{id, song, artist, version, pages, hash, crop?}], setlist: null | {name, items:[{type:'song', id} | {type:'break', name}]}}`, with package-local ids `s1`, `s2`... (never this library's ids). The PDFs are the stored bytes, copied as they are (never re-saved), so a song's SHA-256 is the same on both tablets and the receiver can match songs it already has. It carries details and crops (Jonathan, 2026-11-20) and NEVER annotations, archive flags, timestamps or titles (`title` is derived). A setlist package holds each song it uses once (archived ones too), with its order and breaks. A song with no stored PDF is left out and counted. Sharing changes nothing in the library. `BACKUP_VERSION` and every record shape are unchanged; the package has its own `SHARE_VERSION`. Import (`js/shareimport.js`, Library -> Import a share package): the file is from another person, so everything is untrusted and checked BEFORE anything is written: the file (over `limits.maxPdfBytes + limits.maxJson`, or whose zip directory is over `limits.maxDirectory`, has bytes after its end record, or is zip64 (JSZip builds heap for every record and reads the 64-bit fields), it is refused before it is opened; the zip is opened WITHOUT JSZip's `checkCRC32`, which would inflate every entry just to open it: instead `share.json` is checked against the CRC-32 the zip records for it, and every song's REQUIRED recorded SHA-256 is the integrity check of its PDF), `share.json` (ours, `kind:'share'`, not newer than `SHARE_VERSION`, plain ids via `ID_RE`, short text, a required 64-hex `hash`, a setlist naming only songs in the package, counts within `limits`/`LIMITS`), every PDF (present; read in pieces and counted against what is left of `limits.maxPdfBytes` for the whole package, so a small zip that inflates huge is stopped and never fully inflated; its SHA-256 equal to the recorded one; opens in pdf.js; the page count is pdf.js's, never the file's `pages`), every crop (`cleanCrop` in `js/store.js`: finite numbers inside the page, at least `CROP_MIN`, real page keys; a bad part is dropped and counted, the rest kept). Any other problem refuses the whole package with a plain message and changes nothing. Songs the library already has (same SHA-256, archived ones too) are matched and left exactly as they are; the same PDF twice in a package is one song; nothing is ever overwritten. One import runs at a time (a second pick while one reads or writes is turned away). One confirm dialog (Add / Cancel, naming the setlist as it will be saved) comes first, then an "Adding songs" box covers ONE `putAll()` that writes every new song (fresh ids, made unique with `unique()` because `uid()` can repeat in a tight loop and a repeated key would silently overwrite, details and crop from the package, never archived), its PDF (the packaged bytes, so the hash is the sender's) and the setlist (fresh id and break ids; a name that collides becomes "<name> (2)", "(3)"). A backup given to Import, and a share package given to Restore, each say so. Memory: like restore, every PDF is held in memory before the one write.
- New version (`newVersion()` in `js/library.js`, the button that replaced Replace PDF; Jonathan, 2026-11-21): the song keeps its id, details, crop and setlist places (no setlist is written) and takes the new PDF, `pages` and `hash`; its marks are cleared as before (deletion markers through `reconcile`; ink of pages past the new end removed). The old chart becomes a NEW song (`newSong`, id from `unique()` in `js/shareimport.js`), `archived:true`, in no setlist: the stored PDF bytes copied as they are (hash unchanged), `version` + `old YYYY-MM-DD` (local date, the whole kept within 200 characters: "War Pigs (old 2026-11-21) - Black Sabbath", "(in G, old 2026-11-21)"), the crop, and every page's live strokes and notes under the new id (ids, points, `updated` unchanged; deletion markers not copied). Order: the duplicate question (if the new PDF is already in the library), then one confirm (`modal()`), then ONE `putAll` (files, ink, songs). If the stored PDF cannot be read, the confirm says so, the new chart still goes in and no copy is made. If the song was edited or deleted while the dialogs were open, nothing is written.
- Text notes live in the same ink list as strokes: `{id, t:'text', x, y, text, size, c, updated}`, x,y = top-left as full-page fractions, size = font size as a fraction of page width (small .012, medium .018, large .028). The eraser does not touch them. They undo, print and back up like strokes.
- Set `{id, name, items:[{type:'song', id} | {type:'break', id, name}], created, updated}`. Old sets with a `songs` array are upgraded on load and on restore (`upgradeSet`). A song can appear twice; rows are identified by position. Breaks are not songs: print skips them, the viewer shows a full-screen break page (name and "Next: <song>"), and the song before a break says "Next: <break name>". Reordering is drag and drop from the handle (pointer events, `initSetlists()` in `js/setlists.js`); there are no up/down buttons; with a handle focused, ArrowUp/ArrowDown move the row (keyboard reorder).
- Ink: key `songId:pageNumber` -> `{updated, strokes:[...]}`. A stroke is `{id, t:'pen'|'hl', c:'#rrggbb', w:<fraction of page width>, p:[[x,y],...], updated}`; a pen's `w` is one of three values, thin `.002`, medium `.003` (what the pen always drew) or thick `.005` (`PEN_W` in `js/ink.js`; strokes saved earlier may hold any width and keep it), the highlighter's is `.02`; x and y are fractions (0 to 1) of the full page. Keep them that way. An erased stroke becomes `{id, deleted:true, updated}`. Older data stored a bare array without ids; `upgradeInk()` fixes it on first read.
- Deleting a song or setlist leaves `{id, deleted:true, updated}` in its store (the song's PDF and ink pages are removed). The UI never shows markers; backups include them. This is so a later Google Drive sync can tell "deleted" from "never had it": merge by id, newest `updated` wins.
- Archived songs are hidden from the library (shown with "Show archived"), but still show and play in setlists.
- Small settings live in the browser's own storage, never in IndexedDB: `localStorage` `ss-two` (two pages), `ss-pen-w` (pen thickness: `thin`, `medium` or `thick`; default medium), `ss-last-backup` (time of the last backup download, for the nudge), `ss-problems` (the private problem log: last 30 errors, never sent anywhere); `sessionStorage` `ss-resume` (the open song, put back after an update reload).
- Restore (`restoreFrom`) checks everything first (zip CRC, `library.json` ours and not from a newer version, every song's PDF present and matching its hash) and then writes all four stores in ONE transaction (`putAll`): it is all or nothing. A box (`busy()` in `js/util.js`) says "Opening the backup…", "Checking song N of M…", "Saving to this tablet…"; Stop (or Escape) works while it is only reading and checking and changes nothing ("Restore stopped. Nothing was changed."), and from the write on Stop is gone (`job.lock()`). Back up has the same box ("Packing song N of M…", "Making the backup file… N%"): Stop at any point downloads nothing and does not set `ss-last-backup`.
- Backup is a zip: `library.json` `{app:'setlist-stand', version:2, ...}` plus `files/<id>.pdf`. Version 1 (the prototype and the converter's output) must keep restoring.
- Google Drive connection (Part 1 of the Drive sync work order: sign-in and a test folder; nothing is synced yet). `js/googleauth.js`: "Connect" writes a one-time note (localStorage `ss-google-pending` `{state, t, then}`, a random 128-bit `state`, `then` = what the person had tapped) and sends the whole page to Google's sign-in address (implicit flow, `response_type=token`, the `drive.file` scope only, redirect = the app's own start address computed from `import.meta.url`, no `include_granted_scopes`, no PKCE, no secret). Google returns to the start address with the answer after a `#`. `takeReturn()` is the FIRST thing `js/main.js` runs: it takes the `#` part off the address with `history.replaceState` before anything can fail (the token is not left in the address bar or in the page's own history entry; the browser's separate history list may still keep the address Google sent it back to for the token's life), removes the note whatever the answer says (one answer per trip), and refuses an answer whose note is missing (`foreign`: no sign-in was started in this window), older than 15 minutes (`late`) or whose `state` does not equal the note's (`mismatch`), each with its own plain message; it also refuses `error` answers, a token that is not plain visible ASCII or lives over a day (`bad`), a token that lives under a minute (`short`), and a returned `scope` that lacks `drive.file`. Only then is localStorage `ss-google` `{token, exp}` written (per-device settings like `ss-two`, never in IndexedDB, a backup or a share package); a refused sign-in writes nothing. There is no refresh token: the token lasts about an hour and renewing it sends the page to Google again. `getToken()` is the only reader and returns a token only if it has more than a minute left; it is never logged, shown, put in an address, a backup or a share package (only the `Authorization` header). `js/drive.js` is the thin client (`fetch`, `credentials:'omit'`, abortable): the folder "Setlist Stand" is found by name, type AND a private `appProperties` mark, `trashed = false`, oldest first (two tablets that made one at once agree on the oldest; nothing is ever deleted), made once if missing; listings read every page (bounded; a repeated page token is a broken answer). A failure is a `DriveError` with one plain sentence in `.plain` (`explainError()` returns any error's `.plain`): 401 forgets the token and asks to sign in again; 403 `storageQuotaExceeded` is "Drive is full"; 403 `accessNotConfigured` says the Drive API is off for the project; 429, 5xx and rate-limit 403 are retried a few times with a pause (`tuning` in `js/drive.js`), then "Google is busy"; fetch that gets no answer is "Cannot reach Google" (offline is checked first and nothing is sent). Unexpected failures go in the problem log as kind, status and Google's short code only. `js/syncui.js` draws the Library control (Connect / "Connected until ..." / Test connection / Disconnect) and the plain dialogs; a message stays until OK. Disconnect only forgets the sign-in here (no call to Google). Nothing talks to Google except when the person taps Connect, Test connection or Connect again (or a sign-in trip they started returns), never while a song is open, and a tablet that never taps Connect behaves exactly as before.

## Don't overload Jonathan's Mac
The browser tests start Chromium (and a long run starts hundreds of pages), and helper agents each start their own. Several at once make the Mac crawl. Rules, for Claude and for every helper agent it starts:
- **One browser run at a time.** `tools/smoke.mjs` and `tools/loops.mjs` take a lock (`setlist-stand-browser.lock` in the temp folder; `tools/loops/slot.mjs`) and wait their turn, then wait until the machine's load is below 75% of its cores (up to 5 minutes). Never bypass it: a scratch script that calls `chromium.launch()` must call `await acquireSlot('<name>')` first. `SS_NO_SLOT=1` is for CI runners only.
- **Helper agents:** several may write code at once if each has its own files (that costs the Mac little), but never more than four, and their browser runs all go through the one slot above, so only one of them tests at a time. A helper that is waiting on the slot is fine; starting a second browser on its own is not. Prefer two or three agents; use four only for clearly separate files.
- **Run only what the change needs.** Use `--only <text>` for one loop, not the whole suite after every edit. Run the full `smoke` and `loops` once, at the end of a part. Three clean runs in a row only for a loop that has just flaked, not as a habit.
- For a run longer than a few minutes (the full suite, `plant-faults`), start it as `caffeinate -i node ...` so the Mac does not sleep part-way: a sleep makes timers fire at wake and shows up as bogus failures (a fault "got through" after 30 minutes, a check that "does not parse"). Re-run the single case on its own before believing such a result.
- No watch modes, no polling loops that start a browser, no second dev server while one is running. Check `uptime` before a long run; if the load average is above the core count, wait.
- GitHub runs the full walk after every push (`.github/workflows/browser.yml`); a run on the Mac is for the area just changed.

## Best practices already in place (keep them)
- **Security:** a Content-Security-Policy meta in `index.html` (`'self'` only, no `eval`, no outside hosts except `https://www.googleapis.com` in `connect-src` for the Drive connection, `isEvalSupported:false` for pdf.js); no inline script; no outside request at runtime except those Drive data requests. `tools/checks.mjs` pins the whole policy: loosening it needs Jonathan's OK and a change to the pinned policy in the same commit. `docs/THIRD-PARTY.md` lists every vendored file and its license: add a row and the license text in the same commit as any new vendored file.
- **Data safety:** a backup nudge (banner after 14 days or never), a storage line (used, free, protected or not, "Ask the browser to protect it"), a restore that is all or nothing, a refusal of backups from a newer version, and plain-language errors ("The tablet is full...") through `explainError`. Duplicate PDFs (same hash) are skipped unless Jonathan says "Add anyway".
- **Accessibility and tablet:** every dialog goes through `modal()` (role=dialog, focus trapped and restored, Esc cancels, the page behind is inert); setlist rows reorder by keyboard (handle focused, ArrowUp/ArrowDown); safe-area insets, no rubber-banding or text selection in the viewer, no double-tap zoom delay.
- **Updates:** a new version waits for a tap on "Updated. Tap to reload" (never mid-song); only that tab reloads; the open song comes back.

## Closed-loop tests (`node tools/loops.mjs`)
`tools/smoke.mjs` does an action and checks the result. A **closed loop** takes what an action *produces* (a backup zip, a printed PDF, a deployed file, a reloaded page) and feeds it back through an independent path (restore it, render it with pdf.js, hash it, read the source of truth), then compares with what went in. Nothing is mocked, with ONE exception: real Google cannot be reached from a loop, so `tools/loops/fake-google.mjs` stands in for Google's two addresses at the network edge (Playwright `context.route`); the app's own code, storage, service worker and CSP run for real, and the stand-in behaves like Drive (paging, `fields`, `appProperties`, 401, 403 full, 429, 5xx, CORS). Real Drive is tested by Jonathan on his tablets. Loops live in `tools/loops/*.loop.mjs` (each exports `loops = [{name, needs?, run(ctx)}]`; helpers in `tools/loops/harness.mjs`). `node tools/loops.mjs --list` shows them; `--only <text>` runs some; `--root <dir>` tests a scratch copy; `--live <url>` adds the deployed-site loops; `--seed N --case N --verbose` replays one case of the random loop. A loop whose private input is missing (`needs`) prints SKIP, never FAIL: the MobileSheets files are found in the main checkout's untracked `Claude outputs/` (or `SS_MSB` / `SS_LIBRARY_ZIP`) and are never copied or committed.

## Checks
- `node tools/checks.mjs`: syntax of `js/*.js` and `sw.js`; every precached file exists and every app file is precached; no `http(s)://` in app code (except the four Google addresses in `js/driveconfig.js`, spelled out one by one); the Content-Security-Policy equals the pinned policy; no Google client secret anywhere; no `window.claude`; `VERSION` in `sw.js` changed if a precached file changed.
- `node tools/checks.mjs --bump`: writes a new `sw.js` VERSION.
- `node tools/smoke.mjs`: Playwright run at 1280x800 (add, open, page turns, draw, reload, offline reload, setlist, print, backup/restore).
- Safari engine: `SS_BROWSER=webkit node tools/smoke.mjs` (and `SS_BROWSER=webkit node tools/loops.mjs --only roundtrip` etc.) runs the same walk in Playwright's WebKit (`node node_modules/playwright/cli.js install webkit` once). Chromium-only loops (CDP: update, kill switch, offline h) skip themselves. See `tools/README.md`. Run it after dialog, focus, storage or pointer changes; touch drag on a real iPad is still untested.
- `node tools/lint.mjs`: ESLint (fetched by npx at the versions pinned in `eslint.config.mjs`, nothing installed) for undefined names, dead code and similar slips in `js/`, `sw.js` and `tools/`. Report-only (`--verbose` lists warnings, `--strict` exits 1 on errors); GitHub runs it as the `lint` job.
- Git hooks in `.githooks/` (enable once per clone: `git config core.hooksPath .githooks`). `pre-commit` refuses `.msb`, `.zip`/`.pdf` outside `tests/fixtures/`, anything in `Claude outputs/`, and staged JS that does not parse. `pre-push` runs `node tools/checks.mjs` on a push to `main` (HEAD, clean tree) and refuses on a FAIL; branch pushes pass. Bypass: `--no-verify`.
- Stop hook (`.claude/hooks/stop-checks.mjs`, `.claude/settings.json`): at the end of a turn that changed code files it runs `node tools/checks.mjs` and sends failures back (the "VERSION bumped" line is expected and ignored; at most 3 times a turn). Off switch: `SS_STOP_CHECKS=0`.

## Working with agents
- **Use agents and sub-agents when they fit: this is a rule, not an option.** Hand work to an agent when it is independent of what the main session is doing, is read-only or touches its own files, or needs a view that is not anchored on the main session's: adversarial review (always, for risky areas), a measurement script written while the main session builds, mechanical runs, scouting a subsystem. Do the work yourself when it is a handful of tool calls or a lookup whose answer you need before the next step. Every limit below still applies (at most four at once, one browser run at a time, and a helper that is waiting on the browser slot is fine).
- **The main session decides the model and the effort of every agent it starts, for that job.** Neither is inherited by default and neither is fixed by a table: set `model` and `effort` (`low` to `max`) on each call as the work deserves, weighing how much a missed mistake would cost against the time and tokens spent. Sonnet and Opus are both fine; so is any effort. **Floor for risky cases:** an adversarial review of the data layer, restore, the service worker or print (and anything on the "Never" list) runs on Opus at `high` effort or more: the main session may go higher, never lower, because it is the one whose work is being checked and is least able to judge how hard to look. A work order's own "session effort" line is about the main session and does not cap its agents. Report the choice in one line when it is not obvious.
- **Local agents** work in the worktree and may edit code. Give each its own files, tell it not to touch `CLAUDE.md`, `.claude/`, `.githooks/`, workflows or the `sw.js` VERSION, and keep to at most four at once (see "Don't overload Jonathan's Mac").
- **Cloud agents** (`isolation: remote`) are read-only reviewers. They see only what has been pushed to a branch, so push the branch first and pin the review to that commit.
- **Saved roles:** `.claude/agents/setlist-reviewer.md` (adversarial review) and `setlist-runner.md` (mechanical runs) hold a starting model and effort. They are defaults, not rules: the main session may override either one on a call.
- **Review:** an adversarial reviewer reports findings as file:line, the quoted code, the failing input and the smallest fix. After fixes, a FRESH reviewer re-reviews, not the one that found them.
- **Reports:** at most 20 lines. Treat what an agent says as a claim: read the diff and run the check yourself before relying on it.
- **Rules for each area** are in `.claude/rules/` (service worker, data and backup, viewer and print, dialogs and CSP).
