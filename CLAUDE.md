# Setlist Stand

An installable web app (PWA) for a teacher and gigging musician who plays PDF charts from an Android or iPad tablet. Library of PDF charts, setlists, a full-screen viewer with page turns, pen/highlighter annotation, print and backup. It must work fully offline at a gig. One person per library, no sharing. Scope and settled decisions: `docs/DECISIONS.md`.

## Stack rules
- Vanilla JS as ES modules, plain CSS with CSS variables. No build step, no framework, no bundler: the repo files are the files GitHub Pages serves.
- No external URLs at runtime. Everything loads from this repo, with relative paths (the app lives under `/setlist-stand/`). The one exception (Jonathan, 2026-11-21) is Google Drive: the page may send DATA requests to `https://www.googleapis.com` (the CSP's `connect-src`) and navigates to `https://accounts.google.com/o/oauth2/v2/auth` to sign in. Those addresses, the Client ID and the scope live in `js/driveconfig.js` and nowhere else (`checks.mjs` enforces it). No script is ever loaded from Google (no Identity Services library, no Picker), and there is no client secret anywhere.
- Vendored libs in `vendor/`, exactly: pdf.js 3.11.174, pdf-lib 1.17.1, JSZip 3.10.1. Adding any other library, framework or build step needs Jonathan's OK.
- No music in the repo, ever. The repo is public.
- One job per file. Split a file when it starts doing two things or passes about 300 to 400 lines, and not before: do not cut a file only to make it shorter. Every new app file must be added to `PRECACHE` in `sw.js` (`checks.mjs` fails if it is not).
- Supported tablets: iPadOS 16 or newer, Android Chrome 100 or newer. Do not use a browser feature newer than that without a fallback (theme colours have fallbacks for `light-dark()`).

## Data model (as of v1 part 4)
The full text (every shape, every settled rule, with dates) is in `.claude/rules/data-model.md`; it loads when you touch app or tool files. **Read it before changing anything about records, backup, restore, sync, sharing, New version, Copy song, collections, gig dates or settings.** The short version:

- IndexedDB `setlist-stand`, version 2 (`DB_VERSION`), stores `songs`, `files`, `sets`, `ink`, `colls`. The store names are ONE list, `STORE_NAMES` in `js/store.js`. Raising `DB_VERSION` only creates missing stores and keeps every record.
- Song `{id, title, song, artist, version, archived, colls, pages, hash, added, updated}`; the PDF bytes live in `files` keyed by song id and are never changed. Set `{id, name, items, colls, gig?, created, updated}`. Ink: key `songId:pageNumber`, strokes and text notes with ids, x and y as fractions of the full page. Collections `{id, name, created, updated}`.
- Deleting leaves `{id, deleted:true, updated}`. Every edit of an existing record stamps it with `stamp(prev)`; `putAll` is the one all-or-nothing write (`ifUpdated` refuses a stale one). Records are changed by spreading the old one, so unknown fields survive.
- Songs are matched by id, never by hash, except Add PDFs, share import and split (the known limit). Library order is A to Z by song name, nothing stored in that order.
- Backup is a zip (`library.json` version 3 + `files/<id>.pdf`); restore checks everything and writes in ONE transaction. Small settings live in `localStorage` (list in the rules file), never in the library.
- Google Drive: implicit sign-in, `drive.file` scope, token in memory only, sync only on a tap; details in `.claude/rules/drive-sync.md`.

## Don't overload Jonathan's Mac
The browser tests start Chromium (and a long run starts hundreds of pages), and helper agents each start their own. Several at once make the Mac crawl. Rules, for Claude and for every helper agent it starts:
- **At most two browser runs at a time** (Jonathan, 2026-11-21; it was one). `tools/smoke.mjs` and `tools/loops.mjs` take one of two lock directories in the temp folder (`setlist-stand-browser.lock`, `setlist-stand-browser-2.lock`; `tools/loops/slot.mjs`) and wait for a free one. After taking it, a run waits (up to 5 minutes) until the 1-minute load is below 75% of the cores AND the CPUs were really less than 70% busy over the last two seconds. Never bypass it: a scratch script that calls `chromium.launch()` must call `await acquireSlot('<name>')` first. `SS_NO_SLOT=1` is for CI runners only; `SS_SLOTS=1` gives the old one-at-a-time rule. Measured on this Mac (Intel i5, 8 logical cores, 16 GB; 2026-11-21): idle it sits at a load of 1 to 2.5, each active run adds about 2 (a Chromium run is about 1 core and 600 to 800 MB, plus the node test process), and THREE at once, measured twice, gave a load of 7.4 on average with a peak of 10, and then 5.85 with a peak of 8.4 (the start gate bypassed, a second Claude program busy at the same time): three sits at the limit on average and over it for the first 20 seconds, so TWO is the default; three is possible for one run when nothing else is busy (`SS_SLOTS=3`). A run that is stuck for many minutes at 0% CPU (an orphan whose parent is gone) holds its slot: look at `ps` and tell Jonathan, do not queue behind it.
- **Helper agents:** several may write code at once if each has its own files (that costs the Mac little), but never more than four, and their browser runs all go through the two slots above, so at most two of them test at a time. A helper that is waiting on a slot is fine; starting a browser without a slot is not. Prefer two or three agents; use four only for clearly separate files.
- **Heavy runs go to GitHub, not this Mac** (Jonathan, 2026-11-22). The full `smoke` and the full `loops` run on GitHub's own computers for free (`.github/workflows/browser.yml`, Chromium, about 40 minutes) after every push to `main` and after a push to a branch named `ci-try/<anything>`. So to test a commit before it goes to `main`, push that commit to `ci-try/<work-order>-<n>` (`git push origin <commit>:refs/heads/ci-try/<name>`), then read the result from GitHub (`curl -s "https://api.github.com/repos/jhoffmanteacher/setlist-stand/actions/runs?branch=ci-try/<name>"`; the job annotations name the failing loop and the artifacts hold the whole output) instead of running the whole suite here. Run LOCALLY only: `--only` for what you changed, WebKit (`SS_BROWSER=webkit`), and `plant-faults` (the workflow does none of those). Branches pushed only for tests or reviews (`ci-try/*`, review snapshots) are deleted when the work order is done.
- **Run only what the change needs.** Use `--only <text>` for one loop, not the whole suite after every edit. Run the full `smoke` and `loops` once, at the end of a part. Three clean runs in a row only for a loop that has just flaked, not as a habit.
- For a run longer than a few minutes (the full suite, `plant-faults`), start it as `caffeinate -i node ...` so the Mac does not sleep part-way: a sleep makes timers fire at wake and shows up as bogus failures (a fault "got through" after 30 minutes, a check that "does not parse"). Re-run the single case on its own before believing such a result.
- No watch modes, no polling loops that start a browser, no second dev server while one is running. Check `uptime` before a long run; if the load average is above the core count, wait.
- GitHub runs the full walk after every push (`.github/workflows/browser.yml`); a run on the Mac is for the area just changed.

## Best practices already in place (keep them)
- **Security:** a Content-Security-Policy meta in `index.html` (`'self'` only, no `eval`, no outside hosts except `https://www.googleapis.com` in `connect-src` for the Drive connection, `isEvalSupported:false` for pdf.js); no inline script; no outside request at runtime except those Drive data requests. `tools/checks.mjs` pins the whole policy: loosening it needs Jonathan's OK and a change to the pinned policy in the same commit. `docs/THIRD-PARTY.md` lists every vendored file and its license: add a row and the license text in the same commit as any new vendored file.
- **Data safety:** a backup reminder (`js/nudge.js`, drawn into `#libNudge` on the Library, the Setlists list and an open setlist, never in the viewer): it shows when something has CHANGED since the last backup, not by days (Jonathan, 2026-11-21): any record in any store but `files` (songs, setlists, collections, ink pages, deletion markers) whose `updated` is later than `ss-last-backup`, or, with songs and no backup ever, "You have not backed up yet."; the wording is "Changes since your last backup (today / yesterday / N days ago)." with Back up now. `js/store.js` keeps the newest `updated` in memory (`newestChange()`): `put()`, `putAll()` and `update()` are the only write paths and each tells `seen()` what it wrote once the write has gone through (a plain delete counts as now; a write whose `updated` is not newer, like a restore of old records, a hash filled in or the upgrade's `colls: []`, changes nothing); `load()` reads it from the songs, setlists and collections, `initChanged()` from the ink pages once after the first draw; `ss-changed` is fired when it moves and the reminder redraws without a reload. A restore sets `ss-last-backup` (so a restored library is backed up until the next change); a stopped backup changes nothing. Measured on the 74-song converted library: first Library draw 176 ms before, 185 ms after (noise), the ink scan 15 ms after the draw. Drive sync adds its Sync button to this same line, a storage line (used, free, protected or not, "Ask the browser to protect it"), a restore that is all or nothing, a refusal of backups from a newer version, and plain-language errors ("The tablet is full...") through `explainError`. Duplicate PDFs (same hash) are skipped unless Jonathan says "Add anyway".
- **Accessibility and tablet:** every dialog goes through `modal()` (role=dialog, focus trapped and restored, Esc cancels, the page behind is inert); setlist rows reorder by keyboard (handle focused, ArrowUp/ArrowDown); safe-area insets, no rubber-banding or text selection in the viewer, no double-tap zoom delay.
- **Updates:** a new version waits for a tap on "Updated. Tap to reload" (never mid-song); only that tab reloads; the open song comes back.
- **The back gesture:** an open song and each layer over it (Annotate, the thickness menu, Crop, a dialog) is ONE history entry, pushed only inside the tap that opens it while the browser still counts that tap (`js/backnav.js`: Chrome skips entries pushed without a tap), taken off by `history.back()`/`history.go(-n)` when the layer closes another way, reused (never doubled) after an update reload, dropped at start-up if no song is open. Back means Escape: popstate presses Escape on the top layer (dialog, thickness menu, Crop, Annotate, then the song) and pushes nothing, except under a layer that stays open (a locked dialog, or one opened without a tap: known limit). The Library and Setlists screens add no entry, so back from them leaves the app as before.

## Closed-loop tests (`node tools/loops.mjs`)
`tools/smoke.mjs` does an action and checks the result. A **closed loop** takes what an action *produces* (a backup zip, a printed PDF, a deployed file, a reloaded page) and feeds it back through an independent path (restore it, render it with pdf.js, hash it, read the source of truth), then compares with what went in. Nothing is mocked, with ONE exception: real Google cannot be reached from a loop, so `tools/loops/fake-google.mjs` stands in for Google's two addresses at the network edge (Playwright `context.route`); the app's own code, storage, service worker and CSP run for real, and the stand-in behaves like Drive (paging, `fields`, `appProperties`, 401, 403 full, 429, 5xx, CORS). Real Drive is tested by Jonathan on his tablets. Loops live in `tools/loops/*.loop.mjs` (each exports `loops = [{name, needs?, run(ctx)}]`; helpers in `tools/loops/harness.mjs`). `node tools/loops.mjs --list` shows them; `--only <text>` runs some; `--root <dir>` tests a scratch copy; `--live <url>` adds the deployed-site loops; `--seed N --case N --verbose` replays one case of the random loop. A loop whose private input is missing (`needs`) prints SKIP, never FAIL: the MobileSheets files are found in the main checkout's untracked `Claude outputs/` (or `SS_MSB` / `SS_LIBRARY_ZIP`) and are never copied or committed.

Which loop to run after which change is a table in `.claude/rules/loops.md` (loads when you touch app or tool files). Find your changed file there and run that row's `--only` text; do not run the whole suite locally (GitHub does).

Rules: assert the correct behaviour and never weaken a loop to make it pass; a failing loop is a real gap, so fix the app. `node tools/plant-faults.mjs` plants deliberate mistakes in a scratch copy and requires the right loop to go red (a mistake no loop catches is a gap in the loops; add the test). `context.setOffline` does not cut off the service worker, so offline loops also make the server hang up (`goOffline` in `tools/loops/site-copy.mjs`; `offline.drop` in the smoke test).

## Checks
- `node tools/checks.mjs`: syntax of `js/*.js` and `sw.js`; every precached file exists and every app file is precached; no `http(s)://` in app code (except the four Google addresses in `js/driveconfig.js`, spelled out one by one); the Content-Security-Policy equals the pinned policy; no Google client secret anywhere; no `window.claude`; `VERSION` in `sw.js` changed if a precached file changed.
- `node tools/checks.mjs --bump`: writes a new `sw.js` VERSION.
- `node tools/smoke.mjs`: Playwright run at 1280x800 (add, open, page turns, draw, reload, offline reload, setlist, print, backup/restore).
- Safari engine: `SS_BROWSER=webkit node tools/smoke.mjs` (and `SS_BROWSER=webkit node tools/loops.mjs --only roundtrip` etc.) runs the same walk in Playwright's WebKit (`node node_modules/playwright/cli.js install webkit` once). Chromium-only loops (CDP: update, kill switch, offline h) skip themselves. See `tools/README.md`. Run it after dialog, focus, storage or pointer changes; touch drag on a real iPad is still untested.
- `node tools/lint.mjs`: ESLint (fetched by npx at the versions pinned in `eslint.config.mjs`, nothing installed) for undefined names, dead code and similar slips in `js/`, `sw.js` and `tools/`. Report-only (`--verbose` lists warnings, `--strict` exits 1 on errors); GitHub runs it as the `lint` job.
- Git hooks in `.githooks/` (enable once per clone: `git config core.hooksPath .githooks`). `pre-commit` refuses `.msb`, `.zip`/`.pdf` outside `tests/fixtures/`, anything in `Claude outputs/`, and staged JS that does not parse. `pre-push` runs `node tools/checks.mjs` on a push to `main` (HEAD, clean tree) and refuses on a FAIL; branch pushes pass. Bypass: `--no-verify`.
- Stop hook (`.claude/hooks/stop-checks.mjs`, `.claude/settings.json`): at the end of a turn that changed code files it runs `node tools/checks.mjs` and sends failures back (the "VERSION bumped" line is expected and ignored; at most 3 times a turn). Off switch: `SS_STOP_CHECKS=0`.

## If it goes wrong
`BREAK-GLASS.md` (repo root) is the plain-language page for Jonathan: a bad update on a tablet, a broken site, a lost library. `tools/kill-switch/kill-sw.js` is the emergency service worker that clears the app's caches and never touches the library; `node tools/loops.mjs --only kill` proves it. Keep that page true whenever the service worker or update flow changes.

## Working with agents
- **Use agents and sub-agents when they fit: this is a rule, not an option.** Hand work to an agent when it is independent of what the main session is doing, is read-only or touches its own files, or needs a view that is not anchored on the main session's: adversarial review (always, for risky areas), a measurement script written while the main session builds, mechanical runs, scouting a subsystem. Do the work yourself when it is a handful of tool calls or a lookup whose answer you need before the next step. Every limit below still applies (at most four at once, one browser run at a time, and a helper that is waiting on the browser slot is fine).
- **The main session decides the model and the effort of every agent it starts, for that job.** Neither is inherited by default and neither is fixed by a table: set `model` and `effort` (`low` to `max`) on each call as the work deserves, weighing how much a missed mistake would cost against the time and tokens spent. Agents run on **Opus or Sonnet only**, chosen per job (Jonathan, 2026-11-23): Opus for planning, adversarial review and risky builds, Sonnet for builds from a written plan and for mechanical work; any effort. Never start an agent on Fable or another model, and never let an agent inherit the chat's model: Fable (or whatever model Jonathan set with `/model`) is for the main chat only, and the main session does not change its own model or effort. **Floor for risky cases:** an adversarial review of the data layer, restore, the service worker or print (and anything on the "Never" list) runs on Opus at `high` effort or more: the main session may go higher, never lower, because it is the one whose work is being checked and is least able to judge how hard to look. A work order's own "session effort" line is about the main session and does not cap its agents. Report the choice in one line when it is not obvious.
- **Local agents** work in the worktree and may edit code. Give each its own files, tell it not to touch `CLAUDE.md`, `.claude/`, `.githooks/`, workflows or the `sw.js` VERSION, and keep to at most four at once (see "Don't overload Jonathan's Mac").
- **Cloud agents** (`isolation: remote`) are read-only reviewers. They see only what has been pushed to a branch, so push the branch first and pin the review to that commit.
- **Saved roles:** `.claude/agents/setlist-reviewer.md` (adversarial review) and `setlist-runner.md` (mechanical runs) hold a starting model and effort. They are defaults, not rules: the main session may override either one on a call.
- **Review:** an adversarial reviewer reports findings as file:line, the quoted code, the failing input and the smallest fix. After fixes, a FRESH reviewer re-reviews, not the one that found them.
- **Reports:** at most 20 lines. Treat what an agent says as a claim: read the diff and run the check yourself before relying on it.
- **Rules for each area** are in `.claude/rules/` (service worker, data and backup, viewer and print, dialogs and CSP, Google Drive sync, splitting and sharing).

## Worktree and push rules (from the work order)
- Work in your own worktree, never the main folder: `git fetch`, then `git worktree add ../setlist-stand-wo-<name> -b wo/<name> origin/main`. Run `git worktree list` first; if another worktree has unpushed work in the same files, stop and ask.
- Start every part with `git fetch` and `git rebase origin/main`. Ship each part (push) before starting the next.
- Write `CHANGELOG.md` and bump the `sw.js` VERSION last, after the final rebase, in the part's last commit.
- Push: fetch, rebase if `origin/main` moved, run `node tools/checks.mjs` on the rebased tip, then `git push origin HEAD:main`. Fast-forward only. No merge commits, no force-push.
- If a rebase conflicts in anything besides `CHANGELOG.md` or the `sw.js` version line, stop and ask.
- Files for Jonathan (screenshots, converted backup) go in the main folder's `Claude outputs/`. It is untracked and gitignored; a copy left in a worktree is deleted with it.
- After the last push: fast-forward the main folder if clean, confirm `git cherry origin/main wo/<name>` shows no `+`, then remove the worktree and branch.
