# Data model and settled behaviour (moved verbatim from CLAUDE.md, 2026-11-23)

The short version is in `CLAUDE.md`. This file is the full text; it loads when you touch app or tool files.

- IndexedDB `setlist-stand`, version 2 (`DB_VERSION`), stores `songs`, `files`, `sets`, `ink`, `colls` (in-memory fallback if storage is blocked). The store names are ONE list, `STORE_NAMES` in `js/store.js`: the upgrade, the memory fallback and every loop over stores read it, and `snapshot()` in `tools/loops/harness.mjs` reads the names from the database, so a store added later is carried everywhere. The upgrade from version 1 only creates `colls` (`createObjectStore` for the stores that are missing), so every record, PDF and ink page is kept. A tab still running the old version-1 app blocks the upgrade until it is closed (it cannot be told to let go): `ss-db-blocked` is fired and `js/main.js` says "Close the other Setlist Stand tab"; a tab on this version closes its connection on `versionchange` (`ss-db-changed`: it asks for a reload).
- Song `{id, title, song, artist, version, archived, colls, pages, hash, added, updated}`. `title` is derived: "Song (version) - Artist" (empty parts left out). `hash` is SHA-256 of the PDF bytes. Old records (title only) are upgraded on load with the splitter in `js/names.js` (a port of `split_name()` in `tools/msb_convert.py`; `node tools/names-parity.mjs <.msb>` must print "N of N match"). New imports use `js/importname.js` (title-first file names, legacy names fall back to the splitter). PDF bytes live in `files`, keyed by song id.
- Song order (library, Archived list, search results, the pickers for "Add songs" and "Share songs"): A to Z by song name, `compareSongs` in `js/names.js` (`Intl.Collator`, sensitivity 'base', numeric; ties by artist, version, then id). Every word counts: a leading "The", "A" or "An" is NOT skipped (Jonathan, 2026-11-21). It is made when a list is drawn (`renderLib()`, `pick()`); nothing is stored in that order and no song is written. The order inside a setlist is the user's own. "Add songs" on a setlist picks in TAP order (`pick(…, {ordered:true})` in `js/util.js`): each song tapped gets the next number (shown where the tick box is), tapping a numbered song removes its number and the later ones move up, the button reads "Add N", and the songs are added at the end of the setlist in number order (one number per song per dialog). Every `pick()` has a search box (`songMatches` in `js/names.js`, the same match as the Library's); numbers and ticks survive a search that hides them and the count still counts them; the search box does not take focus on open (the tablet keyboard); Share songs and "Add songs to a collection" are unordered and return list order.
- Song crop (optional): `crop: {all: rect|null, pages: {"<page number>": rect}}`, rect `{x, y, w, h}` as fractions of the FULL page (x, y = top-left of the kept part). A page's own crop wins over `all`. `cropOf(song, pn)` in `js/store.js` is the one place that decides. The viewer draws only the kept part, scaled up; print sets the page's CropBox (after drawing marks against the uncropped page).
- Split a songbook (`js/split.js`, `js/songlist.js`, `js/songpdf.js`): one big PDF becomes separate songs, each saved exactly like an added PDF (the PDF and its record in ONE `putAll`); the book itself is never saved. Pages are copied with pdf-lib after taking off everything that points at other pages, and every song is checked page by page (it holds only its own pages, never part of a chart cut away); a protected, password-locked, layered or ambiguous book is refused, never cut; a run has a space budget; no dates are written, so the same pages always give the same hash and a book split twice is all duplicates. Full rules: `.claude/rules/split-share.md`.
- Share package (`js/sharepack.js`, `js/share.js`, `js/shareimport.js`): chosen songs, or a setlist, as one zip (`share.json` + `files/<id>.pdf`, its own `SHARE_VERSION`) that carries details and crops and NEVER marks, archive flags, timestamps or titles; the PDFs are the stored bytes (never re-saved), so the SHA-256 is the same on both tablets. Import treats the file as untrusted and checks EVERYTHING before anything is written (file and zip limits, the CRC of `share.json`, every PDF's SHA-256, ids, counts, crops); songs already here (same hash) are left exactly as they are, nothing is overwritten, one confirm, and ONE `putAll` writes the lot. Full rules: `.claude/rules/split-share.md`.
- Chart update file (`js/chartfile.js`, `js/chartupdate.js`, `tools/make-chart-update.mjs`; Share / Import -> Import chart updates; Jonathan, 2026-11-22): a zip of cleaned-up charts, each applied as a NEW VERSION of its song (the rest of the library is never touched). `update.json` = `{app:'setlist-stand', kind:'chart-update', version:1, made, charts:[{id, target, song, artist, version, hash}]}` plus `files/<id>.pdf`: `id` a name inside the file (`ID_RE`), `target` the library song id it is meant for (`ID_RE`; may name a song this library lacks), `song`/`artist`/`version` short text, `hash` the required SHA-256 of the PDF. Nothing else travels (no marks, crops, setlists, collections). Read with share import's own checks (exported from `js/shareimport.js`: size, `directoryProblem`, the JSON's CRC-32, `readCapped` against `limits.maxPdfBytes`, every hash, pdf.js page count; at most `limits.maxSongs` charts); any problem refuses the whole file, and a share package and a chart update file name each other's menu item. Matching is BY ID, THEN BY NAME, NEVER BY HASH: the `target` id if it is a live, not archived song; otherwise the one live, not archived song whose song, artist and version compare equal under `compareSongs` (case and accents ignored); otherwise not found. Archived songs are never updated. Rows: Will update (ticked), Already up to date (same hash, no tick box), Not in your library ("Add as a new song", UNticked; made like an added PDF with `newSong`, `joinColls()`, no setlist), Same song twice in this file, or the same PDF twice among the charts offered as new songs (listed, never applied; the first wins; a chart that updates a song and another offered as a new song may carry one PDF, as Copy song allows). "This PDF is also in your library as <title>" is a note only; so are "N songs in your library have this name" (offered as new, never chosen between), "In the file: <name>" (matched by id, named differently in the file) and "Its current chart is not on this tablet: its marks are cleared and nothing goes to Archived". Apply builds each update with `newVersionOps()` (`js/newversion.js`, the same function New version uses, so it does exactly what New version does, crop clearing included), re-reads each target's stored record (a song changed or deleted since is dropped and listed), puts `ifUpdated` on each song op and each of its ink pages' ops (a stroke drawn meanwhile in another tab refuses the batch, never lost), caps the old charts it holds at `limits.maxPdfBytes`, and writes EVERYTHING in ONE `putAll`; a stored PDF that cannot be read skips that song (none stored: no archived copy). One at a time with share import and New version. The result stays until OK.
- New version (`newVersion()` in `js/library.js`; its records are built by `newVersionOps()` in `js/newversion.js`, the button that replaced Replace PDF; Jonathan, 2026-11-21): the song keeps its id, details and setlist places (no setlist is written) and takes the new PDF, `pages` and `hash`; its crop is CLEARED (Jonathan, 2026-11-22: the old layout rarely fits the new chart; the archived old copy keeps it); its marks are cleared as before (deletion markers through `reconcile`; ink of pages past the new end removed). The old chart becomes a NEW song (`newSong`, id from `unique()` in `js/shareimport.js`), `archived:true`, in no setlist: the stored PDF bytes copied as they are (hash unchanged), `version` + `old YYYY-MM-DD` (local date, the whole kept within 200 characters: "War Pigs (old 2026-11-21) - Black Sabbath", "(in G, old 2026-11-21)"), the crop, and every page's live strokes and notes under the new id (ids, points, `updated` unchanged; deletion markers not copied). Order: the duplicate question (if the new PDF is already in the library), then one confirm (`modal()`), then ONE `putAll` (files, ink, songs). If the stored PDF cannot be read, the confirm says so, the new chart still goes in and no copy is made. If the song was edited or deleted while the dialogs were open, nothing is written.
- Copy song (`copySong()` in `js/copysong.js`, the Copy item of a library row's ⋯ menu; Jonathan, 2026-11-21): a second version of a chart (the same chart marked up another way for another band). The copy is a NEW song: fresh id (`unique()`), the original's record carried over by spreading a deep copy (so a field this code does not know is kept), `version` = what the person typed (required; the original's own version, case and spaces ignored, is refused in the dialog), `archived:false`, fresh `added`/`updated`, the same `pages`, `hash` and `crop`; its PDF is the stored bytes copied as they are (hash equal to the original's); every page's LIVE strokes and notes are copied with fresh ids and `updated` (deletion markers not copied). Song, PDF and marks are ONE `putAll`. The copy is in no setlist; the original, its marks and every setlist are untouched. Two songs may therefore share one PDF hash: songs are matched by id, never by hash (Add PDFs, share import and split still match by hash and are the known limit).
- Text notes live in the same ink list as strokes: `{id, t:'text', x, y, text, size, c, updated}`, x,y = top-left as full-page fractions, size = font size as a fraction of page width (small .012, medium .018, large .028). The eraser does not touch them. They undo, print and back up like strokes.
- Set `{id, name, items:[{type:'song', id} | {type:'break', id, name}], colls, gig?, created, updated}`. `gig` is an optional gig date, a plain calendar date `'YYYY-MM-DD'` (no time, no time zone), absent when there is none (Jonathan, 2026-11-22). `js/gigdate.js` (pure: `validGig`, `gigOf`, `cleanGig`, `dateInName`, `groupSets`) reads it, `js/gigui.js` asks for it. A `gig` that is not a real date is IGNORED when a list is drawn (`gigOf`: the setlist sits under "No date", like `cropOf()` ignores a damaged rectangle), dropped and counted by a restore (`restoreFrom()`: "N gig dates that were not real dates were left out"), and NEVER makes `setProblem` refuse a set (sync skips a set that fails it). Changing or clearing it goes through `saveSet` (stamps `updated` with `stamp()`); Duplicate does not copy it; share packages do not carry it (`SHARE_VERSION` and `BACKUP_VERSION` unchanged). The Setlists list is grouped when any setlist has a date: Upcoming (today or later, any year, soonest first), this year's past gigs (newest first), No date, then each earlier year (newest year first, collapsed to start; open or closed is kept in memory only). With no dated setlist the list is flat and has no headers. The one-time fill-in (`offerFill()` in `js/gigui.js`, localStorage `ss-gig-fill`, per tablet, set when the person answers or a write went through): setlists without a gig whose name clearly holds a full date (month name with day and 4-digit year either order, `YYYY-MM-DD`, `M/D/YYYY`; the date must exist; exactly one per name; no lookbehind in the regex, iPadOS 16.0 to 16.3 cannot parse one) are listed with tick boxes; Fill in writes the ticked ones in ONE `putAll` after re-reading each (`gig` and `updated` only, names never change). On a tablet where `driveSetUp()` is true (signed in, or synced before) it is offered ONLY within 10 minutes of a finished sync (`lastSync()`): otherwise this tablet's copy of a setlist may be older than the other tablet's, and the fill-in would stamp the old copy newer so a later sync lets it win (the other tablet's added songs lost); a sync that brings the other tablet's dates in makes those setlists drop out of the offer. A tablet that never uses Drive is offered it as before. Old sets with a `songs` array are upgraded on load and on restore (`upgradeSet`). A song can appear twice; rows are identified by position. Breaks are not songs: print skips them, the viewer shows a full-screen break page (name and "Next: <song>"), and the song before a break says "Next: <break name>". Reordering is drag and drop from the handle (pointer events, `initSetlists()` in `js/setlists.js`); there are no up/down buttons; with a handle focused, ArrowUp/ArrowDown move the row (keyboard reorder).
- Download setlists (Jonathan, 2026-11-21; Download all changed 2026-11-22): the open setlist's item is Download PDF in its More menu (it was the Print PDF button; `printDialog()` and `buildSetPdf()` in `js/print.js` are unchanged apart from the title "Download <name>"): one PDF of its charts in order, with marks if ticked, saved to the downloads, named by `setFileName()` (the gig date first when there is one: "2026-10-18 Sf October 18 2026.pdf"). This is the printing route. Download all (`js/downloadall.js`, the button in the Setlists list bar) is NOT a PDF per setlist (that copied every chart into every setlist and grew with the number of setlists): it makes one zip, `Setlists - Setlist Stand.zip` (`Setlists - <collection> - Setlist Stand.zip` with a collection shown), stored without compression, with `Songs/<title>.pdf` (every distinct chart of the setlists the list shows ONCE, the stored bytes exactly as they are, no marks) and `Setlists/<name>.txt` (one list file per setlist: name, gig date in words, songs numbered and breaks as `--- name ---`; named with the gig date; " (2)" on a clash, case ignored, for songs and for setlists). Setlists with no songs are skipped. A song with no stored PDF is listed with "(no PDF on this tablet)" and named in the final box. Before any work the size of the distinct charts is checked against `limits.maxBytes` (150 MB, an exported object so a test can lower it; the zip is held in memory about three times over) and refused with "Too much to make at once". Stop at any point downloads nothing. Nothing is written to the library and no PDF is changed. `fileName()` in `js/util.js` turns slashes into "-", drops control characters, composes letters (NFC) and cuts to 150 characters.
- Ink: key `songId:pageNumber` -> `{updated, strokes:[...]}`. A stroke is `{id, t:'pen'|'hl', c:'#rrggbb', w:<fraction of page width>, p:[[x,y],...], updated}`; a pen's `w` is one of three values, thin `.002`, medium `.003` (what the pen always drew) or thick `.005` (`PEN_W` in `js/ink.js`; strokes saved earlier may hold any width and keep it), the highlighter's is `.02`; x and y are fractions (0 to 1) of the full page. Keep them that way. An erased stroke becomes `{id, deleted:true, updated}`. Older data stored a bare array without ids; `upgradeInk()` fixes it on first read.
- Collections (`js/collections.js`; Jonathan, 2026-11-21): the band or group a song or setlist is played with, named by him. Store `colls`, record `{id, name, created, updated}`; deleted ones are `{id, deleted:true, updated}` like songs. A song or setlist lists its collections in `colls` (a list of ids, `[]` by default, filled in by `upgradeSong` / `upgradeSet` through `cleanColls`; one song or setlist may be in several; an id of a deleted or unknown collection stays in the record and is ignored when a list is drawn). The upgrade writes `colls: []` on every existing record in ONE `putAll` in `load()` and does not touch `updated`. Names: required, trimmed, at most 200 characters, unique case-insensitively (`askName`). Deleting a collection removes its id from every song and setlist in the SAME `putAll` as its marker and stamps `updated` on each of those records and the marker (a later sync carries a change only when `updated` moves); it never deletes a song, PDF, marks or setlist. Records are changed by spreading the existing one (a field this code does not know is kept; `roundtrip` has a test). Picker under the tabs on the Library and the Setlists list: "All", each collection A to Z (the default marked), and a Collections button (alone until a collection exists); the collection shown is in memory only, so the app opens on the default (or All); an open setlist always plays all its songs; "Add songs" in a setlist lists the shown collection's songs with a "Show all songs" switch (`pick(…, {all})`). Manager dialog (`openManager()`): Rename, Set as default (tap Default again to clear), Add songs, Delete (two taps), New collection. Edit song and an open setlist's Collections button have tick boxes (`form(…, checks)`). New songs (Add PDFs, every split song, share import) and new setlists (New setlist, share import) join the collection shown, or the default when All is shown (`joinColls()`); Duplicate setlist and Copy song carry the original's; New version's archived old chart keeps the song's; a song matched by share import is left as it is. Share packages carry no collections (`SHARE_VERSION` unchanged). Songs are matched by id, never by hash, for collections and Copy.
- Text setlist (`js/setlisttext.js`; Setlists -> Import from a text file; Jonathan, 2026-11-21): at most 1 MB and 500 song and break lines; UTF-8 (byte-order mark removed), UTF-16 with a byte-order mark, else Windows-1252; NUL bytes or more than 2% control characters = not text. Each line, with its number or bullet taken off, is matched to the full title, then the song name, then 'Song - Artist' (case, accents, quotes, dashes and spacing ignored; archived songs count; all songs whatever collection is shown). A song wins over a break (`---`, `===`, `***`, Break, Set break N, Intermission). Lines starting with `#` are ignored. One review box; Add = ONE `putAll` of only the new setlist (`unique()` ids, `joinColls()`, no `gig`, `freeSetName` '(2)'). No song, PDF, ink or other setlist is written and no song is made from a line.
- Deleting a song or setlist leaves `{id, deleted:true, updated}` in its store (the song's PDF and ink pages are removed). The UI never shows markers; backups include them. This is so Google Drive sync can tell "deleted" from "never had it": merge by id, newest `updated` wins. Every place that changes an EXISTING record stamps it with `stamp(prev)` in `js/store.js` (`max(now, prev.updated + 1)`), so a local edit always beats the version it was made from, even a copy from a tablet whose clock is ahead; new records use `Date.now()`. `putAll` ops may carry `ifUpdated` (the `updated` the record must still have, `null` = absent): a mismatch aborts the whole transaction and rejects with an error named `StaleWrite`. The records a deletion writes are built in `js/deleteops.js`.
- Archived songs are hidden from the library (shown with "Show archived"), but still show and play in setlists.
- Small settings live in the browser's own storage, never in IndexedDB: `localStorage` `ss-two` (two pages), `ss-ready` (set to '0' to switch off drawing a played setlist ahead in the background, js/prerender.js; absent = on), `ss-pen-w` (pen thickness: `thin`, `medium` or `thick`; default medium), `ss-gig-fill` (the gig-date fill-in was answered, per tablet), `ss-default-coll` (the id of the default collection, per tablet: never in the library, a backup or a sync; one that points at a deleted collection counts as none), `ss-last-backup` (time of the last backup download, for the nudge), `ss-problems` (the private problem log: last 30 errors, never sent anywhere), `ss-last-sync` (when this tablet last finished a sync, for the sync reminder; never synced), `ss-sync-intro` (the first-sync note was read), `ss-drive-backup` (when this tablet last sent a backup copy to Drive; per tablet); `sessionStorage` `ss-resume` (the open song, put back after an update reload).
- Restore asks first and keeps what it would lose (Jonathan, 2026-11-23): after the checks, a tablet that has any live song, setlist or collection is asked "Restore this backup?" (`js/restoreask.js`: what it adds, brings back, puts back, deletes, keeps and leaves). Any chart, live mark or newer crop the restore would lose (written over or deleted, and not held by a song that stays with the same hash, a readable stored PDF and every mark by content) is kept as an archived copy "(before restore DATE)" through `archivedCopyOps()` in `js/newversion.js` (shared with New version); a setlist changed here after the backup (the backup record's RAW `updated`, missing = 0) is kept as "<name> (before restore)" with each item pointing at whatever holds its chart afterwards. A chart that cannot be read is counted and named in the question and never blocks a restore; past `keepLimits.maxBytes` (300 MB) of copies the question offers "Restore without keeping copies" (two taps). Copies and restore are ONE `putAll` whose ops carry `ifUpdated` (a change made meanwhile refuses it, plainly); a kept setlist copy carries `kept:'restore'`, and a later restore repoints its items in place so it keeps playing what it played; other setlists the restore does not write over keep their items, are NAMED in the question (they play the backup's version of a replaced song), and lose only songs the backup deletes, as a deletion does; a holder is trusted only after its whole PDF reads; restored records keep the backup's `updated`; a backup ink page is written only for a song in the backup; `ss-last-backup` is set only when nothing was kept and nothing outside the backup stays. Loops: `--only "roundtrip over"`.
- Restore (`restoreFrom`) checks everything first (zip CRC, `library.json` ours and not from a newer version, every song's PDF present and matching its hash) and then writes all five stores in ONE transaction (`putAll`; collections too, a deletion marker only winning over a newer collection here): it is all or nothing. A box (`busy()` in `js/util.js`) says "Opening the backup…", "Checking song N of M…", "Saving to this tablet…"; Stop (or Escape) works while it is only reading and checking and changes nothing ("Restore stopped. Nothing was changed."), and from the write on Stop is gone (`job.lock()`). Back up has the same box ("Packing song N of M…", "Making the backup file… N%"): Stop at any point downloads nothing and does not set `ss-last-backup`.
- Backup is a zip: `library.json` `{app:'setlist-stand', version:3, songs, sets, colls, ink, ...}` plus `files/<id>.pdf`. Versions 1 (the prototype and the converter's output) and 2 (before collections) must keep restoring, with no collections. `BACKUP_VERSION` is only the gate in `restoreFrom()`; the per-record checks in `js/backup.js` (`ID_RE`, `LIMITS`, `okId`, `okText`, `okPage`, all exported) do not depend on the version. A song's or setlist's `colls` must be a list of plain ids (a bad id refuses the backup; an unknown id is healed by being ignored), a collection needs a plain id and a short name.
- Google Drive connection (js/driveconfig.js, js/googleauth.js, js/drive.js, js/syncui.js): sign-in is Google's implicit redirect flow, `drive.file` scope only, no server, no secret. The token is kept IN MEMORY ONLY (never in any storage, a backup or a share package: closing the app, a reload or an app update signs out), and only the `Authorization` header carries it. The page's `#` answer is read and removed first thing (`takeReturn()` in `js/main.js`), checked against a one-time note (`ss-google-pending`). The home folder "Setlist Stand" is found by type and a private mark, not by name. Nothing talks to Google except when the person taps Connect, Sync or Connect again, never while a song is open. Full description and the list of failures and messages: `.claude/rules/drive-sync.md`.
- Google Drive sync (js/sync.js, js/syncplan.js, js/syncapply.js, js/syncmarks.js, js/syncink.js, js/syncmerge.js, js/driveops.js, js/syncdialogs.js, js/deleteops.js): started only by a tap on Sync. It syncs songs, setlists and collections as WHOLE records (every field kept) plus each song's PDF, and the pen marks, highlighter and text notes PAGE BY PAGE: merged by stroke id, never newest-page-wins (an erase marker or a later edit beats the older entry; the union of both tablets' strokes is kept), only for a song that is live here and whose chart Drive holds, each Marks file tagged with the hash of the chart it was drawn on, every page from Drive checked and a bad one skipped and named; not per-tablet settings. Merge is by id and `updated` only, never by title or PDF hash (Copy song makes two songs with one PDF): the larger `updated` wins, a deletion marker is just a record, absence is never deletion, and a deletion made on the other tablet is only LISTED (Delete here, two taps / Keep), never applied on its own. Downloads come first, then the person's answers, then uploads; a song's PDF and record are written in ONE `putAll` with `ifUpdated`; a chart a sync would replace is kept as an archived copy; everything from Drive is checked like a restore and a bad record is skipped and named. `ss-last-sync` and `ss-sync-intro` are per tablet. After a FINISHED sync `js/drivebackup.js` may send a backup copy (Jonathan, 2026-11-23): `makeBackup()`'s zip into a marked `Backups` sub-folder the sync's listing never reads, due when Drive's newest copy AND this tablet's `ss-drive-backup` are both 7 or more days old (an empty library makes none; over 150 MB none), the last 4 kept and older MARKED copies moved to the Drive bin (the one agreed exception to the two-tap rule: the app's own copies, recoverable for 30 days), `ss-last-backup` set so it counts as a backup; Stop, a full Drive or an error end only the copy, never the sync. The reminder line also says "Last synced N days ago." after 7 days (`syncStale()` in `js/nudge.js`), from the clock alone: nothing is sent to Google without a tap. Layout in Drive, the order of a run, limits and every rule: `.claude/rules/drive-sync.md`.

- Backup reminder (moved from CLAUDE.md, "Best practices"): a backup reminder (`js/nudge.js`, drawn into `#libNudge` on the Library, the Setlists list and an open setlist, never in the viewer): it shows when something has CHANGED since the last backup, not by days (Jonathan, 2026-11-21): any record in any store but `files` (songs, setlists, collections, ink pages, deletion markers) whose `updated` is later than `ss-last-backup`, or, with songs and no backup ever, "You have not backed up yet."; the wording is "Changes since your last backup (today / yesterday / N days ago)." with Back up now. `js/store.js` keeps the newest `updated` in memory (`newestChange()`): `put()`, `putAll()` and `update()` are the only write paths and each tells `seen()` what it wrote once the write has gone through (a plain delete counts as now; a write whose `updated` is not newer, like a restore of old records, a hash filled in or the upgrade's `colls: []`, changes nothing); `load()` reads it from the songs, setlists and collections, `initChanged()` from the ink pages once after the first draw; `ss-changed` is fired when it moves and the reminder redraws without a reload. A restore sets `ss-last-backup` (so a restored library is backed up until the next change); a stopped backup changes nothing. Measured on the 74-song converted library: first Library draw 176 ms before, 185 ms after (noise), the ink scan 15 ms after the draw. Drive sync adds its Sync button to this same line, a storage line (used, free, protected or not, "Ask the browser to protect it"), a restore that is all or nothing, a refusal of backups from a newer version, and plain-language errors ("The tablet is full...") through `explainError`. Duplicate PDFs (same hash) are skipped unless Jonathan says "Add anyway".
