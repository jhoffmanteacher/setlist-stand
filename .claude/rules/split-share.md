# Splitting a songbook and share packages (moved word for word from CLAUDE.md "Data model", so it is read only when these files are edited)

Change anything here: `node tools/loops.mjs --only split` and `--only share` (and `--only hygiene-ui`); the loop table in `CLAUDE.md` says what each closes.

## Split a songbook

Split a songbook (`js/split.js`): one big PDF becomes separate songs, each saved exactly like an added PDF (`newSong` in `js/store.js`, PDF and record in ONE `putAll`). The book itself is never saved. A draft row is `{id, on, title, from, to}` (`to` null = the page before the next row, rows sorted by `from`, a row that is not ticked still ends the row before it, two rows may share a page). Draft rows come from the PDF's bookmarks (leaf bookmarks only; "Cover", "Contents", "Index" start unticked) or from tapping a page. `makeSongPdf` copies the pages with pdf-lib after taking off everything that points at other pages (Link annotations, and on the other annotations /P, /A, /AA, /Dest, /IRT and a widget's /Parent; on the page /B and /AA): pdf-lib copies whatever a page points at, so one such pointer on every page would put the whole book in every song. Nothing is ever taken out of a page's content or resources (a song must never lose part of a chart). It then counts the page objects it wrote; if the song holds any page besides its own it drops the notes from the song (never from the book) and tries once more, then refuses (`error.cut`) and the song is never saved; a run has a space budget (`budgetFor`: the larger of 150 MB and three times the book; the weight of a song, the size of its streams, is checked before it is saved): a book that makes every song as heavy as the whole book (one list of every picture for all pages) stops the run with a plain message after a few songs instead of filling the tablet, the songs not added stay ticked; one song that cannot be cut does not stop the others. Page dictionaries are never edited by deleting and re-adding a key (that reorders the key and changes the bytes, so the same pages would stop giving the same hash). It writes no dates, so the same pages always give the same bytes and hash: a book split twice is spotted as duplicates and skipped (unless "add again" is ticked); only the library as it was before the run counts, because two songs on one page are the same bytes and both belong. A protected PDF (`isEncrypted`), a password-locked one, one with layers switched off by default (asked of pdf.js) or content tagged with a layer rule (`/OCMD`, as an object or inline; the songs would show what the book hides), and one whose page tree pdf.js and pdf-lib read differently (a song would be cut from other pages than the ones shown) are refused, never cut. Typed titles go through `parseTypedTitle` (taken as typed), not the old-file-name guessing of `parseFileName`. A run that fails or is stopped leaves the screen open with the songs not yet added still ticked. Text notes, crops and marks do not apply: the songs start fresh.

## Share package

Share package (`js/sharepack.js`, `js/share.js`): chosen songs, or a setlist, as one zip with `share.json` and `files/<id>.pdf`. `share.json` is `{app:'setlist-stand', kind:'share', version:SHARE_VERSION, saved, songs:[{id, song, artist, version, pages, hash, crop?}], setlist: null | {name, items:[{type:'song', id} | {type:'break', name}]}}`, with package-local ids `s1`, `s2`... (never this library's ids). The PDFs are the stored bytes, copied as they are (never re-saved), so a song's SHA-256 is the same on both tablets and the receiver can match songs it already has. It carries details and crops (Jonathan, 2026-11-20) and NEVER annotations, archive flags, timestamps or titles (`title` is derived). A setlist package holds each song it uses once (archived ones too), with its order and breaks. A song with no stored PDF is left out and counted. Sharing changes nothing in the library. `BACKUP_VERSION` and every record shape are unchanged; the package has its own `SHARE_VERSION`. Import (`js/shareimport.js`, Library -> Import a share package): the file is from another person, so everything is untrusted and checked BEFORE anything is written: the file (over `limits.maxPdfBytes + limits.maxJson`, or whose zip directory is over `limits.maxDirectory`, has bytes after its end record, or is zip64 (JSZip builds heap for every record and reads the 64-bit fields), it is refused before it is opened; the zip is opened WITHOUT JSZip's `checkCRC32`, which would inflate every entry just to open it: instead `share.json` is checked against the CRC-32 the zip records for it, and every song's REQUIRED recorded SHA-256 is the integrity check of its PDF), `share.json` (ours, `kind:'share'`, not newer than `SHARE_VERSION`, plain ids via `ID_RE`, short text, a required 64-hex `hash`, a setlist naming only songs in the package, counts within `limits`/`LIMITS`), every PDF (present; read in pieces and counted against what is left of `limits.maxPdfBytes` for the whole package, so a small zip that inflates huge is stopped and never fully inflated; its SHA-256 equal to the recorded one; opens in pdf.js; the page count is pdf.js's, never the file's `pages`), every crop (`cleanCrop` in `js/store.js`: finite numbers inside the page, at least `CROP_MIN`, real page keys; a bad part is dropped and counted, the rest kept). Any other problem refuses the whole package with a plain message and changes nothing. Songs the library already has (same SHA-256, archived ones too) are matched and left exactly as they are; the same PDF twice in a package is one song; nothing is ever overwritten. One import runs at a time (a second pick while one reads or writes is turned away). One confirm dialog (Add / Cancel, naming the setlist as it will be saved) comes first, then an "Adding songs" box covers ONE `putAll()` that writes every new song (fresh ids, made unique with `unique()` because `uid()` can repeat in a tight loop and a repeated key would silently overwrite, details and crop from the package, never archived), its PDF (the packaged bytes, so the hash is the sender's) and the setlist (fresh id and break ids; a name that collides becomes "<name> (2)", "(3)"). A backup given to Import, and a share package given to Restore, each say so. Memory: like restore, every PDF is held in memory before the one write.
