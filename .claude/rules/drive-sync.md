# Google Drive: the connection and the sync (moved here from CLAUDE.md so it is read only when these files are edited)

The short version is in `CLAUDE.md` ("Data model"). This file is the full description. The security rule is in `ui-dialogs-csp.md` (rule 5); the data rule for markers, `stamp` and `ifUpdated` is in `data-and-backup.md` (rule 3). Change anything here: `node tools/loops.mjs --only "sync "` (62 loops), and the loop table in `CLAUDE.md` says which loop covers what.

## The connection (Part 1)

Google Drive connection (Part 1 of the Drive sync work order: sign-in and a test folder). `js/googleauth.js`: "Connect" writes a one-time note (localStorage `ss-google-pending` `{state, t, then}`, a random 128-bit `state`, `then` = what the person had tapped) and sends the whole page to Google's sign-in address (implicit flow, `response_type=token`, the `drive.file` scope only, redirect = the app's own start address computed from `import.meta.url`, no `include_granted_scopes`, no PKCE, no secret). Google returns to the start address with the answer after a `#`. `takeReturn()` is the FIRST thing `js/main.js` runs: it takes the `#` part off the address with `history.replaceState` before anything can fail (the token is not left in the address bar or in the page's own history entry; the browser's separate history list may still keep the address Google sent it back to for the token's life), removes the note whatever the answer says (one answer per trip), and refuses an answer whose note is missing (`foreign`: no sign-in was started in this window), older than 15 minutes (`late`) or whose `state` does not equal the note's (`mismatch`), each with its own plain message; it also refuses `error` answers, a token that is not plain visible ASCII or lives over a day (`bad`), a token that lives under a minute (`short`), and a returned `scope` that lacks `drive.file`. Only then is the token kept, IN MEMORY ONLY (Jonathan, 2026-11-21: this app shares its address, `jhoffmanteacher.github.io`, with his other sites, and anything in storage there could be read by a flaw in one of them): never in localStorage, sessionStorage, IndexedDB, a backup or a share package, so closing the app, a reload or "Updated. Tap to reload" forgets the sign-in (an older version's `ss-google` is removed when `js/googleauth.js` loads); a refused sign-in keeps nothing. There is no refresh token: the token lasts about an hour and renewing it sends the page to Google again. `getToken()` is the only reader and returns a token only if it has more than a minute left; it is never logged, shown, put in an address, a backup or a share package (only the `Authorization` header). `js/drive.js` is the thin client (`fetch`, `credentials:'omit'`, abortable): the home folder "Setlist Stand" is found by type AND a private `appProperties` mark (NOT by name: renaming it in Drive changes nothing), `trashed = false`, oldest first (two tablets that made one at once agree on the oldest; nothing is ever deleted), made once if missing; listings read every page (bounded; a repeated page token is a broken answer). A failure is a `DriveError` with one plain sentence in `.plain` (`explainError()` returns any error's `.plain`): 401 forgets the token and asks to sign in again; 403 `storageQuotaExceeded` is "Drive is full"; 403 `accessNotConfigured` says the Drive API is off for the project; 429, 5xx and rate-limit 403 are retried a few times with a pause (`tuning` in `js/drive.js`), then "Google is busy"; fetch that gets no answer is "Cannot reach Google" (offline is checked first and nothing is sent). Unexpected failures go in the problem log as kind, status and Google's short code only. `js/syncui.js` draws the Google Drive box (Library -> Back up / Sync -> Google Drive settings; the bottom of the Library keeps a read-only status line) holding the control (Connect / "Connected until ..." / Sync / Disconnect; the Test connection button was removed 2026-11-23, Sync does the real job, and a pending note an older version wrote with `then:'test'` is read as `connect`) and the plain dialogs; a message stays until OK. Disconnect only forgets the sign-in here (no call to Google). Nothing talks to Google except when the person taps Connect, Sync or Connect again (or a sign-in trip they started returns), never while a song is open, and a tablet that never taps one of them behaves exactly as before.

## The sync (Part 2)

**A Blob read from the `files` store is never stored again as it is** (found by the WebKit loops, 2026-11-22): in Safari it still points at the stored data, so when the original key is overwritten the copy is left with nothing. Copy the bytes (`new Blob([await blob.arrayBuffer()], {type:'application/pdf'})`), as `js/copysong.js`, `js/library.js` (New version) and `keepOldChart()` in `js/syncapply.js` do. Chromium never shows this: run the WebKit loops (`SS_BROWSER=webkit`) after touching anything that stores a PDF.

Google Drive sync (Part 2 of the Drive sync work order). Started only by a tap on Sync (Back up / Sync -> Sync with Google Drive, the Google Drive box, or the reminder line once the tablet has synced), never automatically; a tap while not signed in goes to Google and the sync starts by itself on the way back. It syncs songs, setlists and collections as WHOLE records (every field, including ones this code does not know) and each song's PDF, and (Part 3, below) the marks page by page; not per-tablet settings. Inside the home folder: `Charts` (one `<title>.pdf` per song, properties `{k:'pdf', id, h:<sha-256>}`) and `Library data (do not edit)` (one `<kind>-<id>.json` per record, properties `{k, id, u:<updated>, c:<hash of the canonical JSON>, d:'1' for a deletion marker}`), both found by a private mark; one listing of each says what changed, nothing is downloaded to find out. `js/syncmerge.js` (pure, importable from Node) decides by id and `updated` only, NEVER by title or PDF hash (Copy song makes two songs with one PDF): the larger `updated` wins, a deletion marker is just a record, equal `updated` with other content is settled by the larger canonical JSON text so both tablets pick the same one, absence is never deletion, and a deletion made on the other tablet is only LISTED (Delete here, two taps / Keep) and never applied on its own, not even when it wins a tie. `js/sync.js` carries it out (reading both sides and deciding in `js/syncplan.js`, the uploads, downloads, answers and sweeps in `js/syncapply.js`, the run's shared state in one `ctx` object per run) in this order: survey, the deletion list is shown, everything newer on Drive is DOWNLOADED FIRST, then the person's answers are applied on current data (a deletion edits setlists and collections, so done on an old copy it would date an old setlist as new and beat the other tablet's), survey again, then uploads, then a sweep of the PDF files of songs that are deleted. A song's PDF is uploaded before its record, and a live record uploaded over a deletion marker sends property `d:null` (Drive merges properties on an update; without it a kept song would stay flagged as deleted). A download is one song at a time, the PDF must start with `%PDF-` and its SHA-256 must equal the record's `hash`, and the PDF and the record are written in ONE `putAll` that only goes through if the local record still has the `updated` that was read (`ifUpdated`); everything from Drive is checked like a restore (`songProblem`, `setProblem`, `collProblem`, exported from `js/backup.js`, plus: `updated` is a number equal to the listed one, the file's `d` property agrees with its `deleted` flag, a crop is kept as it is and `cropOf()` ignores a damaged rectangle) and a bad record or PDF is skipped and listed by name, never written; a file Google refuses is skipped, five in a row end the run. A download that would replace this tablet's chart of a song with a DIFFERENT one keeps the old chart and its marks as an archived copy in the same write (unless this tablet already holds those bytes under another song): a sync never loses a chart. A record is compared after `normalize()` (the upgrade `load()` applies), so an upgrade is never a conflict. Limits (`LIMIT` and `CAP` in `js/sync.js`): a PDF of 100 MB, 500 MB of PDFs and 50 MB of record files per run, a Drive folder with more than 20000 songs, 5000 setlists or 2000 collections is refused (his library is 74 PDFs, 43 MB, the largest 2.3 MB); an upload up to 5 MB is one request, a larger one is a resumable upload that needs Google to let the page read its `Location` header (unverified on a real tablet). `js/driveops.js` holds the Drive calls, `js/syncdialogs.js` the first-time note, the deletion list and the report. `ss-last-sync` (this tablet only) is set when a run finishes (to when its last survey began) and drives the "Changes since your last sync" reminder in `js/nudge.js`, which counts songs, setlists, collections and ink pages (`newestRecordChange()` in `js/store.js`, `RECORD_STORES`; what a sync writes with `fromSync` is not a change to sync, and `syncPending()` marks one when a sync leaves this tablet's own marks not yet on Drive); a record dated more than a day ahead is ignored when it is only read and counts as "now" when it is written (`seen()` in `js/store.js`), so a tablet with a wrong clock can neither hide real changes from the reminders nor keep one on; a sync never clears the backup reminder, because sync is not a backup.

## The marks (Part 3)

Pen, highlighter and text notes follow the person through the same Sync, **merged per page by stroke id** (`mergePage` in `js/syncink.js`, pure; never newest-page-wins): every id of either side is kept, the larger `updated` wins per id (an erase marker or an edit beats an older stroke; a tie goes to the marker, then the larger canonical text), the result is live strokes then markers by id, the same on both tablets. Drive: a third sub-folder `Marks (do not edit)` (mark `{setlistStand:'ink'}`, found like the other two; made only at the first page that has to be sent, `ensureInk`, so a full Drive still downloads everything as in Part 2; absent, the ink listing is empty), one `ink-<songId>-<page>.json` per page holding `{updated, strokes}`, properties `{k:'ink', id, p, u, c, h}` (`parseInkProps`; `h` is the SHA-256 of the chart the page was drawn on: a file without a usable `h` is a stray; a Drive page is merged only when its `h` is this tablet's song hash; a page of another chart is never merged: this tablet's page replaces it, else it is left alone; two files for one page: larger `u`, oldest, smaller id). A page with no entries is never uploaded; one of only markers is. `js/syncmarks.js` carries it out: per page, only here -> sent; only on Drive -> merged into an empty page and written; the same `c` -> nothing; else Drive's is merged with this tablet's, written here if that changed here, sent if it changed Drive's. **A song's marks sync only while it is live here AND Drive holds its chart** (Drive's PDF has the song's hash, or this run put it there): marks never revive a song, never go up for a song Drive deleted or lacks, never cross charts while a newer chart has not come down; pages past the song's `pages` are neither written nor sent: a Drive page past the end is listed under Skipped, except that the run that puts a new, shorter chart on Drive removes the old chart's pages past its end (their marks are on its archived copy); a Drive page of a song that is neither here nor in Drive's records is listed; one whose song is on its way (not down yet, a deletion asked about) waits silently. A song that comes down brings its pages in the SAME `putAll` as its PDF and record (`ifUpdated` per page); `keepOldChart` merges this tablet's old marks (live ones AND erase markers) into an archived song only if that song ARRIVED IN THIS RUN from Drive (`ctx.arrived`; never an unrelated song that merely shares the PDF: songs are matched by id, never by hash), holds the same bytes and all its marks are this song's own by id; else a separate copy, as before (so a copy that came down in an earlier run is doubled, nothing is lost). Every ink write there carries `ifUpdated`. Other pages: one small `putAll` per page after the uploads (a `StaleWrite` counts as changed meanwhile). A Drive file is replaced only while its `c` (read again just before) is the one merged; else the next sync merges both. Every page from Drive is checked before anything is written: `LIMIT.page` 5 MB (= one upload request; a few thousand ordinary strokes), streaming cap, JSON, nesting depth 32, `inkProblem` + `inkShapeProblem`, `updated` = listed `u`, canonical hash = listed `c`; a bad page is skipped and listed (`<song>: page N: <why>`), never fatal; at most `LIMIT.pages` (2000) pages read per run, their bytes counted in `LIMIT.records`; five refusals in a row (pages counted apart) end the run; more than `CAP.ink` (100000) page files refuses the run. This tablet's own pages are checked the same way before they are sent. A deleted song's Drive pages are swept like its PDF. Report: `Sent marks on N page(s).` / `Got marks on N page(s).` (got = a page whose shown marks changed here). Loops: `--only "sync ink"` (the merge, Node), `--only "sync 6"`.

Review rules for marks (2026-11-22, an independent review of the first build): a song's marks sync only when Drive's record is THIS tablet's (this run sent it live, or the last look had no unsettled work for it: no refused upload, skipped download, deletion question or unreadable record, and Drive's record is live) AND Drive's PDF is its chart (listed so, or put there by this run): a PDF that went up before Drive refused the record does not count (`unsettled()`, `ctx.downNow`, `ctx.pdfOn`), otherwise one tablet's erase markers for the old chart could reach Drive while the other tablet still shows that chart. Drive full while sending marks is remembered, sending stops, receiving goes on, and the 'full' error is thrown at the end (a full Drive still downloads everything). Pages this tablet could not send (skipped, refused, too big, Drive full) count as pending for the SYNC reminder only (`syncPending()` never moves the backup reminder's time). A live entry needs a colour `#rrggbb` (print cannot read anything else); a page is checked with `inkProblem`, `inkShapeProblem` (which covers `MAX_U`) and the nesting depth BEFORE it is sent, never sent if the other tablet would refuse it. `inkRecord` keeps the stored page's unknown page-level fields; an old id-less stroke gets the id `'l' + index + '-' + FNV-1a(JSON)` so two tablets that restored the same old backup derive the same ids (random ids would double the page after a sync). Known and accepted: a duplicate Drive file for one page (the folder race) is not removed and stays a Skipped line; a local page that can never be sent keeps the sync reminder on until it is fixed.


## The backup copy and the reminder (2026-11-23)

Backup copy in Drive (`js/drivebackup.js`): after a FINISHED sync (after `ss-last-sync` is written, never when the run was full, stopped or failed), a weekly copy of the whole library is sent to a marked `Backups` sub-folder (mark `{setlistStand:'backups'}`, made at the first copy, never listed by `listLibrary`). The file is `setlist-stand-backup-YYYY-MM-DD.zip`, exactly `makeBackup()`'s blob, properties `{k:'backup', t:<ms when packing began>}`.
- Due when the newest marked copy's `createdTime` and this tablet's `ss-drive-backup` (per tablet, never synced) are both 7 or more calendar days old; this tablet's own fresh note means no request at all; an empty library makes none; over `limits.maxBytes` (150 MB, as Download all) none.
- After the send, `ss-last-backup` is set to the time packing began (a copy counts as a backup). The last 4 are kept; older marked files go to the Drive bin (`trashed:true`); unmarked files and files outside the folder are never touched.
- Stop, a full Drive and any error end only the copy, and the report says which. `driveBackup()` never throws.
- The sync's order, counts and `strays` are unchanged. Loops: `--only "sync backup"`.
- Not yet proven on real Google: the resumable upload (every copy over 5 MB). Jonathan tests it on a tablet.

Sync reminder (`syncStale()` in `js/nudge.js`): "Last synced N days ago." after 7 days on a tablet that has synced, from the clock alone. The automatic "your other tablet has changes" check (playtest-2 Part 2) was NOT built: the sign-in lasts an hour and lives in memory, so it would rarely run. Nothing talks to Google without a tap. Loops: `--only "sync reminder"`.
